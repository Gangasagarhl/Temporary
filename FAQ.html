introHow is a 5 GB file read "packet by packet"?

Think of the file as a very long paper tape. The program does not cut the tape into pieces. It pulls the tape past a reader one line at a time. It reads one row, does its work on that row, throws the row away, and pulls the next. Row 1,000 and row 1,001 are never in different pieces, because there are no pieces. A 5 GB file and a 5 KB file go through the same reader. Only the time differs.

But some rows belong together. A question at row 1,000 may get its answer at row 49,000. The program does not keep the rows for that. It keeps a small notebook of "things still waiting". The question leaves a note. The answer, when it comes, finds the note and crosses it out. A note still open at the end of the tape is a question that never got its answer. Each note is a few numbers, and notes are crossed out as soon as their partner arrives, so the memory stays small however long the tape is. One million rows used 26 MB.

What the program writes down is small too. A finding is the packet number, the time, the rule name and a short note, never the row itself. No rule may write more than 100,000 findings; after that it only counts. So one noisy rule cannot fill the memory on a 33-million-row file.

Example

Row 1,000 is a read question. The program writes a note. Then 48,000 unrelated rows go by. Row 49,000 is the answer. The program finds the note by its number, checks it, and crosses it out.

FAQ 1What is the notebook, really?

It is two things in the program's memory, both in the file stage1/pcie_isolate/engine.py.

  • A set of labelled boxes, called self.out. The label on a box is the pair (who asked, which tag). Inside the box: the packet number of the question, the time it was sent, which direction, what kind, the address, how many bytes are still owed, how many have come, and a mark that says "already too late". You go straight to a box by its label. You never open the other boxes.
  • A queue, called self.out_heap. In it the open questions stand in the order they were sent, oldest at the front. The program only ever looks at the front.

Example

Row 1000: the host (its id is 000:00:0) asks to read 64 bytes, tag 7, at time 10.000 s. Rows 1003 and 1010: two more reads, tags 9 and 12. Now there are three boxes and three in the queue.

boxes self.out:
  (000:00:0, 7)  -> [row 1000, sent 10.000, Downstream, MRd, 0x80000000, owes 64,  got 0, late? no]
  (000:00:0, 9)  -> [row 1003, sent 10.001, ..., owes 128, got 0]
  (000:00:0, 12) -> [row 1010, sent 10.002, ..., owes 32,  got 0]
queue self.out_heap (front first):
  (10.000, row 1000, (000:00:0, 7))   <- the oldest
  (10.001, row 1003, (000:00:0, 9))
  (10.002, row 1010, (000:00:0, 12))

Row 2400: an answer comes for tag 9 with 64 bytes. The program reads two columns of that row, RequesterID and Tag, makes the label (000:00:0, 9), and opens that box: owes 128, got 0, becomes owes 64, got 64. The box stays, because bytes are still owed. Row 2401: 64 more bytes for tag 9. Owes 0. The box is taken away. Its place in the queue stays, and will simply be skipped later.

Row 60000 arrives at time 10.060 s. The program looks only at the front of the queue: tag 7, sent at 10.000, so 60 ms old. The limit is 50 ms. That is a finding: TXN.CPL_TIMEOUT at row 1000. The box is marked late and the front is removed. New front: tag 9. Its box is gone, skip. New front: tag 12, 58 ms old, also too late. Queue empty, stop. Three looks, whatever else is in the file.

Why two things and not one? The boxes answer "is there an open question with this label?" in one step. The queue answers "which open question is the oldest?" in one step. One list could do one of these fast, not both.

FAQ 2How does an answer find its question?

Think of a cloakroom. You hand in a coat and get a ticket with a number. Later you show the ticket and get the right coat back. PCIe works the same way. A question that needs an answer, such as a read, carries two things: who asked (the Requester ID) and a ticket number (the Tag). The answer carries the same two things back. That pair is the label on the box.

In the trace file these are the columns RequesterID and Tag, present on both the question row and the answer row. The column TLP Type says which is which: MRd or CfgRd0 is a question, Cpl or CplD is an answer. The answer row also has CompleterID (who answered), Cpl Status (did it work), Byte Cnt (bytes still to come) and Lwr Addr (where this piece starts). A write needs no answer, so it has no ticket.

The helper packets have their own pairing. Every packet sent carries a running number in the column PSN. The "got it" helper packet (DLLP Type ACK) names that number in AckNak Seq Num.

FAQ 3How is "too late" decided, and who sets the limit?

There are two ways to be too late.

  • The tape ends and the box is still open. The question never got its answer. Finding: "no completion by capture end".
  • A new row arrives, and the oldest open box is older than the limit. Finding: "completion timeout". If the answer still arrives after that, a second finding says "the completion arrived, but late".

The limits are not guessed. They are written in one table in engine.py called THRESHOLD_SOURCES, and each limit says where it comes from. Every run also writes the limits it used into its record file, run.json, so anyone can check them later.

FAQ 4What are credits?

Credits are permission slips. Before anyone sends work packets, the receiver says: "I have room for this many packet headers and this many chunks of data" (a chunk is 16 bytes). Those numbers are the credits. They are given at the start, when the link comes up, in helper packets called InitFC. Later the receiver keeps handing out more slips with helper packets called UpdateFC, as it empties its room. The sender may only send while it still has slips. If it sent more, the receiver would have nowhere to put the packet and would have to drop it.

The analyser counts the slips for each direction and for each kind of packet (posted, non-posted, completion) and reports a packet sent without a slip. The columns: DLLP Type (InitFC1-P, InitFC2-P, UpdateFC-P, and the same for NP and Cpl), HdrFC (header slips), DataFC (data chunk slips), and each work packet's Length.

Example

An InitFC1-P with HdrFC 2 and DataFC 8 means: room for 2 headers and 8 chunks, so 128 bytes of data. One write of Length 16 (that is 64 bytes) costs 1 header slip and 4 chunk slips. After two such writes all slips are used. A third write must wait for an UpdateFC-P.

FAQ 5Rule, finding, defect, isolation and error type: one small capture, step by step

Start with a picture from school. A teacher marks homework. The marking rules are written down ("a sum must add up", "a sentence must end with a full stop"). Every time a rule is broken, the teacher puts one red mark on that line. The teacher writes "one mistake: misread question 3, first went wrong at line 12" and decides whose fault it was (the child, or an unclear question). FAQ 6What is the evidence, and what is the second read? (a diary, sticky notes and a photocopier)

A story. Imagine a diary with 33 million pages (the capture: 33 million rows, 5.8 GB). You are asked: "find every day something went wrong, and bring me photocopies of those pages so I can see for myself". You cannot photocopy all 33 million pages: the copier's tray (the computer's memory) holds a few thousand. And you cannot know which pages matter until you have read on: a page that says "I lent my bike to Sam" only becomes a problem if, fifty pages later, the bike still has not come back.

So you do it in two passes:

  1. First read. Read the diary from page 1 to the end, one page at a time, keeping only a small notebook (FAQ 1). Whenever a rule breaks, write a sticky note: "page 1003: bike not returned after 50 pages". A sticky note is a finding. You copy no pages. When you reach the end you have, say, 30 sticky notes and zero copies.
  2. Group the sticky notes into defects (FAQ 5). Now you know exactly which pages you want to show: the page with the question, the page with the late answer, and the pages between them; nothing is added around them.
  3. Second read. Open the diary again at page 1, flip forward, and photocopy only the wanted pages. The moment you pass the last wanted page, stop; the rest of the diary is never opened again. The photocopies are the evidence.

What the evidence is used for. It is what the Defect page shows as "the rows" and the ladder (FAQ 27, 38), what the AI reviewer is given for its second opinion (FAQ 33, call 1), and what the comparison on the Report page points at. It is the proof; the findings are only the claims.

Why not do it in one read? Two reasons. Memory: holding 33 million rows would need far more than the machine has, while the evidence of a whole capture is a few hundred rows. Knowledge: during the first read the program does not yet know what will matter; a request becomes evidence only when its answer turns out late, and a row becomes context only after the groups are known. Reading twice costs time (the second read is as fast as the first), but it is the only way that works on any file size with a fixed amount of memory.

Where in the code. The first read is engine.py run(). The grouping is incidents.py cluster(). The second read is the class Extract in incidents.py: it is given the sorted list of wanted packet numbers, reads the file line by line from the top, copies a row when its packet number is wanted, and returns as soon as the last wanted number has been passed. Rows without packet numbers (analyzer error rows) are skipped. The engine itself never keeps rows; it keeps findings.

FAQ 9An answer that nobody asked for, and a question number used twice

The two words you need. A question is a packet that needs an answer: a read (MRd) or a configuration read or write (CfgRd0, CfgWr0). An answer is a completion packet (Cpl or CplD). Every question carries two columns that name it: RequesterID (who asked, for example 000:00:0 is the host) and Tag (a small number, 0 to 31 normally). The answer carries the same two values. So the name of a question is the pair (who asked, tag), for example (000:00:0, 31).

What the engine keeps. While reading, it keeps a list of open questions: questions that have been asked and not yet fully answered. Each entry says the name, when it was asked, and how many bytes are still owed. A full answer removes the entry. (FAQ 1 calls this list the notebook.)

Two things can go wrong with the names.

Why an answer nobody asked for happens. Three usual reasons: the question was sent before the recording started (then the engine also reports CI.CAPTURE_START and gives this finding less weight); the question was already fully answered and the drive sent one answer too many (a drive bug: data could land in a buffer the host has reused); or the answer is very late, after the host gave up and the engine already closed the question as a timeout (then it is reported as TXN.CPL_LATE instead).

Why a number is used twice. There are only 32 numbers (256 with extended tags), so a busy host goes round and round through them. Reusing a number whose question is finished is normal. Reusing one that is still open is the fault: the next answer with that number cannot be matched to the right question. The usual cause is a host driver that hands out numbers wrongly, or a host that gave up on a question after its own time limit and reused the number while the drive was still answering. FAQ 11Damaged packets and "send it again"

Every packet ends with a check number, the CRC. The receiver works the number out again from what it got. If the two differ, the packet was damaged on the way. FAQ 16Drive commands, doorbells and registers

A drive command is a 64-byte note the host writes into a list in its own memory, called the submission queue. The host then rings a doorbell: it writes a number into a special address of the drive, meaning "the list now has this many notes". The drive reads the note, does the work, and writes a 16-byte reply into another list in host memory, the completion queue. These rules need to see the bytes inside the packets. They come from the DATA column when it holds the bytes, otherwise from a separate file called the payload sidecar.

The notebook here is open[(queue number, command id)]. Each box holds the time of the doorbell, the time the note was fetched, the data moved, and the reply.

FAQ 22Finding timeouts without checking everything

Checking every open question against the clock on every new row would be far too slow: thousands of checks, 33 million times. The trick: questions are opened in time order, so the one sent first is the one that will be too late first. The queue keeps them in that order and hands over the oldest in one step. On every new row the program does only this:

  1. Look at the front of the queue, the oldest open question.
  2. Is "now" minus its send time more than the limit? If no, stop. Everything behind it was sent later, so nothing else can be too late either.
  3. If yes, write the timeout finding, mark the box, drop the front, and look at the new front. Repeat until the front is young enough.

Example

Limit 50 ms. Front: tag 7, sent at 10.000 s. A row at 10.020 s: 20 ms, one look, stop. A row at 10.055 s: 55 ms, too late, remove; new front tag 9 at 10.001, 54 ms, too late; tag 12 at 10.002, 53 ms, too late; tag 15 at 10.040, 15 ms, stop. Four looks instead of thousands. A question whose answer came earlier was already removed from the boxes; when it reaches the front of the queue it is skipped.

FAQ 23Drive commands on PCIe: which layer, and how they look

NVMe has no packets of its own on the wires. Everything it does is done with ordinary PCIe reads and writes, the work packets (TLPs). The analyzer records them like any other packet. What makes them NVMe is the address they go to and the bytes they carry:

  • The host sets a drive register by writing to an address inside the drive's window (BAR0; 0xFCE00000 in the sample).
  • The host rings a doorbell by writing 4 bytes to BAR0 + 0x1000 + 8 × queue number.
  • The drive fetches a 64-byte command note from the host's memory.
  • The drive writes a 16-byte reply into the host's completion queue, then 4 bytes to raise an interrupt.
  • The data of a read or write moves as memory writes or reads between the host's memory and the drive.

The helper packets underneath (ACK, NAK, credits) only make sure these work packets arrive. They know nothing about commands.

FAQ 24How were the rules made?

Where each rule comes from is now written next to the rule. stage1/pcie_isolate/rules.py ends with a table called SOURCE: for every one of the 227 rules it gives where (the document and section: PCIe Base 4.0, NVMe 2.0, the NVM Command Set, SMBus 3.1, NVMe-MI, the Teledyne analyzer manuals, the Linux NVMe driver, or the project's own catalogue and methods) and why (what failure the rule is evidence of). The same two texts are attached to each rule as spec and why, so any page can show them. A test (stage1/tests/test_rule_sources.py) fails if a rule is added without a source.

No rule was written from a guess. Each one walked the same path, in seven steps.

  1. Source. A rule book or a trusted document says what must happen: the PCIe rule book (packets, helper packets, wires, time limits, credits), the NVMe rule book (registers, queues, command and reply formats, status codes), the Linux driver's time limits where the rule book gives no number, the analyzer vendor's manuals for its own 72 error kinds, and the SMBus and IPMI rule books for the side wire.
  2. Card. Every known error type, 485 of them, was written up as a card (data/atlas_cards_raw.json): what happens, how it shows in a trace, which rule it comes from, usual causes, who is to blame.
  3. Pattern. Each card was tied to one of 27 trace patterns (P01 to P27): which columns carry the proof and how the rows relate, for example P03 "a question with no answer past the limit" or P07 "credits".
  4. Rule entry. One line in rules.py: the name, the tier (A = one row is enough, B = memory across rows, N = needs the bytes inside the packets, S = counting over the whole trace, H = the host's records), whether it is a defect or only a note, what it proves on its own, which layer, the patterns, and a plain sentence.
  5. Code. The check in engine.py, in the part that handles the right kind of row, using the notebooks. Any number it needs is a named limit in THRESHOLD_SOURCES with its source written beside it.
  6. Test. A small made-up trace with a known right answer, in stage1/tests. The rule must fire there and must stay quiet on a healthy trace. There are also 485 made-up scenarios, one per card, and real trace samples that must give no false alarm. 62 tests run on every build.
  7. Matching. When the program runs, the patterns of a defect's rules say which cards are likely, so the defect gets the right name, and the AI reviewer is handed the card's text to judge against.

Example

FAQ 25Why does step 1 ask for each of its boxes?

Think of the analyser as a doctor. The trace is the X-ray: it shows what happened on the wires. But a doctor also wants the patient's name, the blood test, and the notes from the family. Each box of step 1 is one more piece of that picture. Only two boxes are required: the trace file and your name. Every other box is optional, and the page tells you what you lose without it. Here is each box: what it is, why it is asked for, what happens without it, and an example.

1. Analyzer CSV path (required)

What it is. The trace: the 113-column table the analyzer software saved. One row per packet. Why. Without it there is nothing to check. How it is used. The path is checked by services.safe_path: spaces and quotes are removed, and the file must lie under a folder the administrator allowed in config/app_config.json. The file is read in place; nothing is copied. Example. C:\Users\admin\Desktop\csv_data\1hi.csv. If the same file is given again with the same other boxes, the earlier run is opened instead of running again; the box "analyse again even if this file was analysed before" forces a new run. The program knows it is the same file from its path, size and change time, and from the other boxes, hashed together by services.run_key.

2. Payload sidecar (optional, only for size-only exports)

What it is. A second file with the bytes inside the packets, for exports whose DATA column only says the size, such as "256 B", instead of the bytes themselves. Why. Every drive command is a 64-byte note inside a packet, every reply a 16-byte note, every doorbell a 4-byte number. The rules for commands, replies, doorbells, registers and data (the families NVME, DB, REG, DATA, and the CFG family) read those bytes. With sizes only, those rules cannot run at all, and step 2 shows a yellow warning "analysed with limited inputs". Format. One row per packet that has data: Packet, nbytes, head_hex, crc32, built by the analyzer's "expand data" export or by stage1/tools/build_payload_sidecar.py. Example. A real analyzer export usually already has the bytes in DATA, so this box stays empty. If the export shows "64 B" where the command note should be, you need the sidecar. Code. engine.py opens it as PayloadSidecar and reads the bytes by packet number while it reads the trace.

3. Find companion files next to the CSV (a button)

What it does. Looks in three places, the folders <trace>_outside_evidence and <trace>_sidecars and the trace's own folder, for files with known names: payload_sidecar.csv, dmesg_x.txt, host_events.jsonl, Errors.csv, and a manifest with the namespace size. It fills the boxes it finds. Why. So you do not type five paths by hand. Code. runs_api.find_inputs; it only reads folder names, it changes nothing.

4. Analyzer error summary, Errors.csv (optional)

What it is. The analyzer software's own list of 72 error kinds with counts, saved from its Reports › Error Summary screen as a CSV (columns Type, Upstream, Downstream, Sideband, Total). Why. It is the answer key. With it, step 2 shows a table: each kind, the analyzer's count, this analysis's count, found or not, and the reason when not. That is how you know whether this program finds what the analyzer finds. Without it the analysis runs the same; only the comparison table is missing. Example. C:\Users\admin\Desktop\Errors.csv, the file from your pictures: 33 kinds with non-zero counts, 14,307 bad LCRCs. Code. stage1_runner runs the verify step; verify.py analyzer_record compares counts kind by kind; the table comes from runs/<run>/analyzer_check.json.

5. Linux kernel log, dmesg -x (optional, recommended)

What it is. The host computer's own diary, one line per event with a time and a severity. The host writes there when a drive command times out, when it resets the drive, when the link goes down. Why. About 46 of the 485 known error types leave no trace on the wires at all: a driver timeout, a decision inside the host, a management action. The trace cannot prove them. The log can. Also, the log tells the host's side of the story: "I waited 30 s and gave up" explains a reset that the trace alone would call unexplained. Without it such defects are reported as "Needs evidence" and the blame cannot be settled. Example line. [1234.567] nvme nvme0: I/O 17 QID 1 timeout, aborting. The fuse step turns 1234.567 s of host time into trace time, using one event both saw, and attaches the line to the defect whose command id is 17. Code. host_evidence.py; the rule family H.

6. Host tool records, host_events.jsonl (optional, recommended)

What it is. Records from the other tools on the host, one JSON line each: {"time": seconds, "source": "nvme-log" or "smart-log" or "fio-verify" or "blktrace" or "bmc" …, "level": "err", "text": "…"}. Why. The drive's own error log and health log (nvme-log, smart-log), the data checker's result (fio-verify), the host's I/O timing (blktrace), the management controller (bmc) each prove things the wires cannot: that the drive itself logged the error, that the data read back was wrong, that the host side was slow. Without it those proofs are missing and the matching defects stay "Needs evidence". Example line. {"time": 1234.9, "source": "fio-verify", "level": "err", "text": "verify: bad magic header at LBA 0x1F400"} attaches to a DATA.MISCOMPARE defect at that time. Code. the same fuse step as the kernel log.

7. Your name (required)

What it is. The person running the analysis. Why. Every run and every stage 2 decision is recorded with the person who made it, so later anyone can see who analysed a trace and who judged a procedure. Decisions that need two people (retiring a procedure, removing a cause) check that the second name differs from the first. Code. stored as operator in the run's parameters and in the meta of every event in knowledge.sqlite (stage2_service._event_meta). The browser remembers it for next time.

8. Device under test (optional)

What it is. The drive's model or name. Why. Procedures and regression tests are filed per device model and firmware, because the same error needs different tests on different drives. When the trace holds the drive's answer to the Identify Controller command, the analyser reads the model, serial and firmware from the packets itself; type a name only to override that or when the trace has no such answer. Code. the device name and the firmware label are hashed into the context_hash (stage2_v3.present), which labels every saved procedure; a procedure from another device shows as "seen on another device or firmware" and is re-checked in the lab before it is trusted.

9. Namespace size, nsze (optional)

What it is. How many blocks the drive's namespace has, as the drive reports it in Identify Namespace; written in hex, for example 0x3A386030, which is 977,000,496 blocks. Why. A read or write that goes past the last block is an error (the rule NVME.SQE_LBA). Without the size the analyser cannot tell a legal read near the end from one past it, so that rule stays off. If the trace itself contains the Identify Namespace answer, the analyser reads the size from the packets and this box is not needed. Code. Engine.nsze; the check "start block plus block count beyond the namespace size".

10. Firmware label (optional, default FW-A)

What it is. A name for the firmware the drive ran during the trace. Why. Stage 2 files procedures under the firmware. When you tell it the firmware changed, what was learnt on the old firmware counts half (the counters a and b are halved), because a fix may have changed the drive's behaviour. The lab check also uses "known-bad firmware" and "fixed firmware" as two sides: 6 runs must show the error on the first and 3 runs must stay silent on the second. Example. 11. Run label (optional)

What it is. Free text so you recognise the run later in the list, for example "field return 2026-10 unit 7". Why. Run ids are made from the clock (run-20261027-080333-cb05) and say nothing about the trace. Code. stored with the run; shown in the Earlier runs list and in the reports.

FAQ 26How is the kernel log used to map an error, and where is it shown?

The kernel log and the trace are two diaries written by two different clocks. The log says "at 1234.567 s the host gave up on command 17". The trace says "at 10.061 s packet 61000 arrived". To use the log, the program must first learn how the two clocks relate, then move each log line onto the trace's clock, then find the packet that was on the wires at that moment, then put the line next to the defect it belongs to. This is the "fuse" step, in stage1/pcie_isolate/host_evidence.py. It runs only when a log was given, and it is step 3 on the Analyse screen: "Line up the host evidence with the packets".

Step 1. Read the lines

Each line of dmesg -x looks like kern :err : [ 1234.567890] nvme nvme0: I/O tag 12 (100c) opcode 0x2 QID 3 timeout, aborting. The program takes the severity (err), the time in seconds since the host booted (1234.567890) and the text. Plain lines without the severity, [ 1234.567890] text, are accepted too.

Step 2. Keep only the lines that matter

A line is kept when its severity is a warning or worse, or when its text contains an error word: error, timeout, timed out, fail, abort, reset, corrupt, miscompare, mismatch, lost, stall, throttle. Everything else is ordinary chatter and is skipped. The run record counts how many were kept and how many skipped (benign_skipped in host_alignment.json).

Step 3. Line up the two clocks

The program needs one event that both diaries record. It uses a controller reset. On the wires a reset is the host writing 0 into the control register (the rule REG.CTRL_RESET, a write to BAR0 + 0x14 with the enable bit cleared). In the log it is the line "resetting controller". Each log reset time minus each wire reset time gives a difference; the most common difference, refined by the middle value of those within 2 ms of it, is the clock offset. The record keeps the sentence "anchor pairs: 2 kernel 'resetting controller' lines vs 2 wire CC.EN=0 writes, 2 matched". If there is no reset on either side, the clocks cannot be lined up and the step says so; a known offset can then be given by hand.

Step 4. Move each line onto the trace's clock and find its packet

trace time = log time − offset. The program keeps a time index from the first read, the time of every sixteenth packet, and looks up the last indexed packet at or before that time. Lines whose time falls before the first or after the last packet are counted as "outside the capture window" and dropped. Because a host writes its log a little after the event on the wires, an optional "snap" setting moves the line onto the latest wire defect found up to a few milliseconds before it.

Step 5. Give the line a rule

The text is matched against a catalogue of message classes, and becomes a finding of the H family at that packet: "timeout" or "reset" or "I/O error" or "AER" or "iommu" lines become H.KERNEL_ERROR with the class noted; "verify", "miscompare", "checksum" become H.DATA_VERIFY; "smart", "error log", "telemetry" become H.NVME_LOG; "bmc", "firmware", "acpi" become H.PLATFORM; "latency", "irq", "blktrace" become H.HOST_TRACE; "analyzer", "filter", "buffer wrap" become H.CAPTURE_SETUP. No card name is ever read from the text; only the words decide. The findings go to host_findings.pkl.

Step 6. Join the wire defects

The isolate step joins a host finding to a wire defect only when the fusion placed it on the packet of a wire finding (clock alignment to the same packet, FAQ 26) or a finding refers to it; there is no distance rule. A group of host lines that stands alone up to 50 packets before a wire group is joined to it, because the host logs after the wires show the event. Inside the defect the host line is one more finding with its packet, its time and its text.

Step 7. What changes in the result

Each defect has a status. When the wires alone prove the error, it is "isolated". When the wires show only the symptom and the proof needs a document, it is "needs host evidence", and the record lists which document (for example "E03 nvme error log with the same queue and command id"). When the needed line is present, the status changes and the Defect page says: "Host evidence was needed and was taken from the host", then shows the source (dmesg), the packet it was placed at, the text of the line, and "why this source". The run page's defect summary shows the same in one line: "needed and taken from dmesg: '…'". When no log was given, step 2 shows a yellow warning that fewer defects are visible than the trace contains, and the defect says "needed, not yet available", with the list of documents to collect.

FAQ 27The "What the packets showed" ladder: where every piece of it comes from

On the stage 2 card, under "What the packets showed", you see a ladder: two vertical lines marked HOST and DEVICE, one arrow per packet going from one to the other, a time gap on the left (Δt), the packet number on the right, grey bands saying "— 50 ms gap, no traffic —", and one shaded row marked "◂ first abnormal". Nothing on it is drawn by hand or by a model. Every mark comes from a row of your trace, through four steps.

Step 1. The rows are cut out during the first analysis (stage 1)

When findings are grouped into a defect (FAQ 5), the program notes the defect's first and last packet and the "key" packets, that is every packet a finding points at. It then takes a window of 15 rows before the first packet and 15 rows after the last (the constant CONTEXT_ROWS in incidents.py). When the defect is long, it keeps two windows, one around the start and one around the end, plus the key packets on their own. The second read of the file (FAQ 6) copies exactly those rows. Each row is written as compact text, "column=value" pairs joined by bars, for example Packet=37389 | Link Dir=Upstream | TLP Type=Cpl | Tag=7 | Time Stamp=0001.2396…, with the file line number and, when the bytes are known, the payload. All of this goes to runs/<run>/incident_rows.jsonl, one line per defect.

Step 2. The screen asks for them

When you open a defect in stage 2, the browser calls GET /api/runs/<run>/incidents/<defect>. The server (stage2_api.py) returns the defect record and its row blocks from that file. The browser's parseRows in decision.js splits each compact row back into its columns.

Step 3. Each row becomes one line of the ladder

  • Which side the arrow starts from: the column Link Dir. Downstream is drawn from HOST to DEVICE, Upstream from DEVICE to HOST. A row with no direction (a link event) is a dot in the middle.
  • The words on the arrow: built from the row's type and a few columns by the function label. An ACK or NAK shows its AckNak Seq Num: "ACK · seq 1602". A memory read or write shows its Address and Length: "MWr(64) · 00000004:80450150 · 4 DW". A configuration packet shows its Register: "CfgWr0 · register 0x044". An answer shows its Tag, or its Cpl Status when that is not "successful": "Cpl · tag 7", "Cpl · status UR".
  • Δt on the left: this row's Time Stamp minus the previous row's, in microseconds. "+0 µs" means less than half a microsecond.
  • The grey gap bands: when Δt is 1 ms or more, a band is drawn first with the words "— 50 ms gap, no traffic —". It means nothing at all crossed the wires for that long. Long gaps are often the most telling part of the ladder: the device went silent.
  • The packet number on the right: the column Packet, so you can find the row in the trace file or in the analyzer software.
  • Colours: the shaded row is the defect's "first abnormal" packet, the one the first rule fired on; blue rows are evidence packets that findings point at; grey rows are link-layer acknowledgements (ACK and NAK); the rest are plain.

Step 4. Which rows are shown

The short view keeps the 12 rows around the first abnormal packet, leaving out acknowledgements unless they are evidence, so the story fits one screen. The link "show every row" switches to the full windows, up to 300 rows, acknowledgements included.

Reading your example

Your ladder shows the host restarting the drive and checking whether it comes back. Packet #37385 is a write to BAR0 + 0x101C: a doorbell. #37387 and #37391 are configuration writes to register 0x044, the power-state register, 50 ms apart: the host puts the drive to sleep and wakes it, a reset by power state. #37395, the shaded first abnormal row, is a read of BAR0 + 0x1C, the status register CSTS, 2 ms after the wake-up; the answer #37398 is "Cpl · status UR": the drive refused the read. That refusal is the first wrong packet, so the rule fired there. 20 ms later #37400 writes BAR0 + 0x14, the control register: the host switches the drive on again. #37402 and #37406, reads of the status register 1 ms and then 999 µs apart, now get real answers (CplD, tags 10 and 11): the host is polling for the "ready" bit. #37410 reads BAR0 + 0x00, the capability register, 2 DW. The FEE03000 write at #37382 is an interrupt message to the host's interrupt address. In short: after a power-state reset the drive answered its first status read with a refusal, and the host went through the switch-on sequence again.

The sentences above the ladder

  • "the top one reproduced the defect in at least 68 % of lab runs (likely)": 68 % is the Wilson lower bound of successes over runs when the procedure was last validated (FAQ formulas), and the word in brackets is a fixed scale on that bound: very likely at 80 %, likely at 50 %, possible at 25 %, unlikely below.
  • "0 correct · 0 corrected · 0 removed · 1 undecided": counts of your decisions on the cards of this defect so far.
  • "earlier decisions on this error type: 10 correct, 1 not correct": the counters a − 1 and b − 1 of this error type's procedures in the knowledge base, rounded, that is what every admin decided before on the same error type.

FAQ 28The Report page: triage, regression tests, known-bad and fixed firmware, optimal, and every number on it

The Report page is the scoreboard. It answers one question: did the product do its job, and how fast? To read it you need five words first.

The five words

  • Triage. A hospital word. At the emergency desk a nurse looks at each patient for a minute and sorts them: who is urgent, who can wait, what is probably wrong. That first quick sorting is triage. Here, triage is stage 1: the first look at a trace that says "there are 3 defects, this one is a timeout, this one is a controller fault, and the drive is to blame". The product statement says that first look must take at most 10 minutes. That is the first-level triage limit. A run that takes longer counts as a fail on this page.
  • Regression test. A regression is a bug that comes back after someone changed the firmware. A regression test is a small test you keep and run again after every change, to make sure an old bug stayed fixed. The whole point of stage 2 is to turn a defect found in the field into such a test.
  • Known-bad firmware and fixed firmware. Two drives, or two versions of a drive: one with the bug, called known-bad, and one where the bug is said to be fixed. A good test must show the error on the known-bad drive, and must stay silent on the fixed drive. If it also fires on the fixed drive, the test is wrong, not the drive.
  • Failure signature, or fingerprint. The identity of an error type as the product sees it: the catalogue card plus the rule that fired first plus the layer. Two defects with the same fingerprint are "the same error seen again". The knowledge base keeps one entry per fingerprint.
  • Optimal. The product statement's own rule: a procedure is optimal when the lab check scores above 0.9 three times in a row. The score of one lab run is checks passed out of 3: the analyser found the same error type, by the same rule, and confirmed it. So "optimal" means: three lab runs in a row where all three checks passed.

A story to hold it together

A drive came back from a customer. Stage 1 looked at its trace for 52.9 seconds and found 3 defects. Stage 2 then took each defect to the lab bench (a simulated drive, or the real hardware bench when one is connected). For Defect 1, a timeout, it searched for a command sequence that makes the timeout happen again. After 37 lab runs it found one: "flush, then write". FAQ 29What is the "lab", why is it needed, and which function makes it?

Stage 1 reads a trace and says "this is a timeout, the drive is to blame". That is a diagnosis from one recording. Stage 2 wants more: a recipe that makes the fault happen again on purpose, so a test can guard against it. You cannot prove that a recipe works by reading; you must run it on a drive, record what happens, and look. The place where that happens is the lab, also called the bench in the code. A lab run is: take a procedure (a list of commands with timing and a power state), send it to a drive, capture the packets, and run the analyser on the capture. The lab answers one question each time: did the same error appear?

Why it is needed

  • A proposed procedure, from the AI reviewer or from the knowledge base, is only a guess until it has been run. The lab turns the guess into a fact with a number: reproduced in k of n runs.
  • The optimiser (FAQ interactive part 5) needs a reward for each try. The lab gives it: how far did this try get towards the same error (stage 0 to 4) and how close was it.
  • The regression test needs proof on both sides: the error appears on the known-bad drive and stays away on the fixed drive. Only lab runs can show that.
  • Minimising and the stress search ask "does it still fail?" after each change. Each answer is a lab run (2 of 3 runs must still fail).

Two kinds of lab

The built-in simulated lab. No hardware is connected on most installations, so the product ships with a stand-in drive. It is the class GeneratorBench in stage2/testgen.py. Inside it sits a pretend drive, SyntheticDeviceOracle in stage2/oracle.py, which holds a secret: for each error type a hidden recipe (a small sequence of commands, a queue depth, a timing window, sometimes a power state) that makes "its" fault appear, with a bit of randomness so it fails only most of the time, like a real flaky drive. Nobody tells the optimiser the secret. The optimiser has to find it by trying, exactly as it would on real hardware. When a try hits the secret, the bench asks the synthetic trace generator (data/generator/) to write a trace that contains that error, saves it in a working folder (stage2/closed_loop_out/bench_<error type>/), and runs the stage 1 analyser on that trace. So the loop is complete: the analyser must find the error in a capture, the same way it did on the customer's trace. The fixed bench is the same class with fixed=True: its pretend drive never fails, and a "decoy", a neighbouring error type, can be injected so that staying silent is not trivially easy.

The hardware lab. When a real bench exists, you write the two methods of app/bench_hook.py HardwareBench: run(scenario), which sends the commands to the real drive, captures the packets with the analyzer and returns the capture path, and detect(trace), which runs the analyser on it (a template is in deploy/bench_hook_template.py, and the manual is deploy/BENCH_INTEGRATION.md). You switch to it with the Bench setting; the service then uses _bench_factory in app/stage2_service.py, which hands HardwareBench to stage 2 instead of the simulated one. Nothing else changes: the optimiser, the lab check and the tests see the same two methods.

Which function makes the lab

  1. The admin presses a decision that needs lab runs (Correct, Needs changes, Add a procedure, Try nearby variations, Generate test cases).
  2. stage2_service.act starts a background job; _execute_job calls stage2_v3.execute.
  3. execute builds the two benches with self.bench_factory(sig, family, expected, fixed, decoy, seed): once with fixed=False (known-bad) and once with fixed=True (fixed). The factory is GeneratorBench by default, HardwareBench when configured.
  4. The optimiser's oracle wraps the known-bad bench: every try is bench.run(scenario), and the reply gives stage, closeness, reproduced and the findings.
  5. verify_closed_loop in testgen.py runs the final procedure 6 times on the known-bad bench and 3 times on the fixed bench and scores each run (FAQ 28).
  6. The test files are written so the same two benches are used later by pytest through conftest.py.

"showed the error in at least 68 % of lab runs". This number is not the plain success rate. If the recipe worked 8 times out of 8, the plain rate is 100 %, but eight tries is not much evidence. "Your decision": the counters

Every cause and every procedure carries two numbers, a (how often admins said Correct) and b (how often they said Not correct), starting at 1 and 1. A verdict event adds r to a and 1−r to b, with r = 1 for Correct and r = 0 for Not correct. Older verdicts fade: each new verdict first multiplies both counters by 0.98 (gamma 0.02), so last year's ticks weigh less than today's, and the counters are capped at 50 so one procedure cannot become untouchable. A firmware change halves both (0.5), because the drive is not the same drive any more. "Revise" (changing the stored text) shrinks both by 0.7, because the thing that was voted on has changed. The prior 0.50 you see on a fresh candidate is simply a/(a+b) with a = b = 1: no opinion yet. Your card's saved procedure says "admins said Correct 10 times, Not correct 1 time": those are the raw verdict counts from the event list; the faded a and b behind them are what the ranking uses. All of this is in stage2/kgdb.py (_credit, the parameters gamma, cap, fw_halve, edit_shrink), and FAQ section 5 lets you play with it.

Top candidates: "lookup match 73 %" and "why it matched"

The lookup (stage2/retrieval_v3.py) looks for saved cases that resemble this defect in three ways, then merges the three lists:

  1. Words: the error type name, the rule names and the evidence sentences, compared as text (BM25-style word overlap).
  2. Meaning: the same text as embeddings (a list of numbers that is close for similar sentences) when an embedding model is available; otherwise a character-shingle similarity.
  3. Structure: the same error type, the same rule family, the same device family.

The three lists are merged with reciprocal rank fusion: a case that is 1st in one list and 3rd in another scores 1/(60+1) + 1/(60+3). Then every fused score f is scaled by the two learned signals:

final = (f / f_top) · √(0.5 + 0.5 · post) · exp(0.5 · tanh(pl))
post = a / (a + b)          the admins' Correct share, 0.50 when nothing is known yet
pl   = the Plackett–Luce ranking strength learned from drag-to-rank events (η = 0.3)

"why it matched: text similarity 0.81, prior 0.50" is just those pieces shown. One slot in the top list is an exploration slot: a lower-ranked case drawn at random with weight Beta(a, b) (Thompson sampling), so a good case that admins have not had a chance to vote on can still appear and collect votes. Without that slot the first lucky case would be shown forever.

Proposal (call #4 answers). {"commands":[write, flush, aspm_idle, read], "timing":{"qd":4, "inter_cmd_us":50, "burst_len":16, "idle_gap_ms":120}, "power_state":"D3hot", "mechanism":"the idle gap puts the drive into D3hot; the read arrives inside the 10 ms recovery window"}. Code checks every word and number against the allowed lists. The card shows it with "prior 0.50".
  3. Admin presses Correct. Backend: verdict event r = 1, then a lab job. Because nothing is saved yet, the mode is "generate": the proposal becomes the seed of the search. The error family's standard trigger shape is always added as a second seed.
  4. Search (stage2/optimizer.py, FAQ 30 table). Up to 300 trials. Each trial applies one of 14 small edits to the current recipe (halve a timing, double it, change the power state, add or drop a command, swap two commands…), chosen by a Thompson-sampled bandit that learns which edits help. The device model (or the bench, if "Search on: bench") answers each trial with a reward = stage reached + closeness. Example: trial 7 shortens idle_gap_ms to 90 and the model says "stage 3, closeness 1.0, reproduced". If nothing reproduces from the model's seed, one retry starts from the family template with another random stream.
  5. Confirm. The best recipe is re-run 8 times; it is confirmed only if the Wilson lower bound of its hit rate is at least 0.5 (so at least 6 of 8).
  6. Minimise. Steps are removed one at a time while 2 of 3 runs still reproduce: the flush turns out to be unnecessary; the recipe is now write, aspm_idle, read.
  7. Most-stressful step (if the setting is above 0). Each timing is pushed in its harder direction while the error still appears: inter_cmd_us down to 25, qd up to 8. The hardest recipe that still works is kept as a second candidate.
  8. Closed loop on the bench (stage2/testgen.py verify_closed_loop). 6 runs on the known-bad bench, 3 on the fixed bench; each run = run the recipe, capture, run the stage 1 engine, score the three checks. Pass = at least one hit on bad, none on fixed. Example: 6/6 and 0/3.
  9. Manifest (test_manifest). A dictionary with: the incident id, the error type, the final recipe (steps, timing, power state), the expected error types the engine may report for it, the two firmware names, the Wilson lower bound measured in step 5 or 8, a hash of the context, the admin and the lessons, and the verdict rules. One number is computed here: how many repeats the future test needs so that a defect that reproduces with probability p is seen at least once with 95 % confidence: n = ln(0.05) / ln(1 − p), clamped to 3…20. With p = 0.61 that gives 4 repeats; with p = 0.2 it gives 14.
  10. Render (render_closed_loop_pytest). The fixed template is filled with the manifest: a MANIFEST constant, a SCENARIO built from it, and two test functions: test_known_bad_reproduces_and_detector_isolates (run the recipe n times on the bad bench, run the stage 1 detector on each capture, require at least min_hits isolations) and the fixed-firmware test (the same recipe must stay silent). emit_closed_loop_test writes three files into runs/_bench/…/tests/<test id>/: manifest.json, test_<id>.py, conftest.py (the fixtures that connect bench and bench_fixed to the same bench factory, synthetic or hook).
  11. Events. A solution_validate event stores the lower bound and the test paths; the card's Result block shows "37 lab runs · known-bad 6/6 · fixed 0/3 · tests: …".

So the model's whole contribution to the test file is the starting point of step 3. Steps 4 to 10 are deterministic code and bench runs, and the search is free to change every word of the model's recipe. That is also why the test is trustworthy: it was not written by anyone; it is the recipe that actually reproduced the error on the bench, wrapped in a template.

FAQ 34Finding, defect and error type, told with the analyzer's Errors.csv: what each one is, how a defect becomes "one episode with one root", and where the three live in the code

The three words in one line each.

  • A finding is one packet where one rule was broken. ("packet 7 310 251: the TLP's LCRC does not match", rule DLL.LCRC_BAD)
  • A defect is one episode: all the findings that happened close together in the capture, with the first abnormal packet marked as the root and the later ones marked as follow-ons (cascade) or independent. A defect is not a category.
  • An error type is the category stage 2 gives to a whole defect, named after its root (the T-numbers in the knowledge base). Many defects in many captures can share one error type.

What the Errors.csv is, and what it is not

The file you photographed (72 rows: Type, Upstream, Downstream, Sideband, Total) is the analyzer's own count sheet. The left column is the name of a rule the analyzer checks (its 72 kinds; the app maps each to its own rules, FAQ 7). Each number is a number of findings: packets flagged with that kind, in that direction. Example rows from your file:

How a defect is built, step by step ("like how?")

  1. Take only defect-level findings. Every rule has a level. Defect-level rules (a bad LCRC, a timeout, an invalid code) can start or join an episode. Context-level rules (a reset, a host action, a link-up) cannot start one; they are attached to a nearby episode as background.
  2. Sort them by packet number and walk through them once. Each finding covers a small range of packets (itself and the packets it is related to, for example a timeout covers the request and the moment the clock ran out).
  3. The linking rule. Two findings join one group when they name the same identifier (the pair RequesterID + Tag of a transaction, PCIe 4.0 §2.2.6.2; the TLP sequence number, §3.5.1; the NVMe command SQID + CID, NVMe 2.0 §4.1; a queue or an LBA), when one refers to the packet of the other (its rule looked at that packet: a completion and its request, a lost command and the reset that lost it, an early access and the D0 write before it), or when they sit on the same packet. Nothing else joins them. An identifier names one instance: a tag only while its request is outstanding (PCIe 4.0 §2.2.6.2), a command id only while that command is open (NVMe 2.0 §4.1), a sequence number only inside the unacknowledged window (PCIe 4.0 §3.5.1), so the engine attaches the packet that opened the instance to the key, and the same tag number used again an hour later is a different key. Queue numbers name long-lived objects and do not join findings. There is no packet distance and no time distance in the rule; an earlier version used a 1000-packet gap, which was an engineering assumption and was removed.
  4. Attach context. Context findings (host actions, resets, link-ups) are kept only when a defect finding refers to them or sits on their packet; a context finding on its own is not a defect. Findings with no identifier and no reference at all (symbol errors, bad codes, ordered-set faults) are reported as one series per rule and qualifier with a count, the way the analyzer's Error Summary counts them; no cause is claimed between them.
  5. Find the root. Inside the group the first abnormal packet is the root. The published cascade table (CASCADE in incidents.py, from the PCIe and NVMe catalogue: "a physical-layer error can cause a bad LCRC, which can cause a NAK, which can cause a replay, which can cause link recovery…") draws CAUSES arrows from earlier findings to later ones. A later finding that has an arrow pointing at it is a cascade; one that has none is independent (it happened in the same window but is not explained by the root).
  6. Blame (attribute()): from the set of rules in the group and the direction of the root packet, a fixed list of reasoning rules names who is responsible: device, host, platform, link or test setup, with the evidence that would settle it. The ladder on the Report page (FAQ 27) is this episode drawn as a diagram.
  7. Error type (stage 2): the root's rule points to a catalogue card; the card and the rule family give the signature, the T-number. Two defects whose roots fall on the same card get the same error type, even if their cascades differ in length.

FAQ 35What a "Thompson sample" is, and where the program uses it

One sentence. A Thompson sample is one random draw from a curve that describes how good an option probably is; the program lets every option draw once and takes the option with the highest draw. It is a way of choosing while still unsure, without always picking the current favourite and without picking at random.

A story. You have 14 friends who each claim to know a shortcut. For each friend you keep two counts: a, how often their shortcut was faster, and b, how often it was slower, both starting at 1. Before each trip, instead of always asking the friend with the best record, you let every friend roll a special dice. A friend with many wins rolls a dice that almost always lands high. A friend you have never tried rolls a dice that can land anywhere. You follow whoever rolled highest. Over many trips the good friends win most rolls, but an untried friend still gets a turn now and then, which is how you find out whether they are good.

The dice: Beta(a, b)

The curve is the Beta distribution with the two counts as its shape. Its average is a ÷ (a + b), the plain rating. Its width shrinks as a + b grows.

a, bwhat was seenplain rating a ÷ (a + b)what one draw looks like
1, 1nothing yet0.50anywhere between 0 and 1, all equally likely
9, 18 wins, 0 losses0.90almost always above 0.75
2, 61 win, 5 losses0.25almost always below 0.5
45, 544 wins, 4 losses0.90tightly around 0.9; the option is well known

Example with two of the optimiser's edit operators

trial"halve a timing", a = 9, b = 1"swap two commands", a = 1, b = 1pickedwhy
1draw 0.88draw 0.31halvethe favourite usually wins
2draw 0.91draw 0.95swapthe unknown option can draw high; it gets a turn and its counts update
3draw 0.86draw 0.12halveback to the favourite

A greedy picker (always the best rating) would choose "halve" forever and never learn about "swap". A random picker would waste half the trials on known-bad edits. Thompson sampling is in between, and the share of trials given to a worse option shrinks as the evidence against it grows. Nothing is trained; it is counting plus one random draw.

FAQ 39"Generate test cases" and "Try nearby variations": what each does, why, how they work in the backend, with two small simulators

The two buttons in one sentence each. Generate test cases starts from what the knowledge base already knows (the saved procedures for this error type) and asks the AI reviewer to compose up to three new recipes from them; each is proved in the lab before it becomes a test. The narrative and the AI reviewer. Each block carries a short text (headline, what happens, what to tell the team). The code first writes it from the facts alone. When a model is set up, the AI reviewer is asked once per kind, after the facts are computed, and gets nothing but those facts. Its answer is accepted only if every number in it appears in the facts, it names no side the facts do not name, it asserts no cause of its own ("caused by", "root cause", "bug in" are rejected), and it is short. Otherwise the fact-built sentences are shown and the source line says why. So the text can be read by a manager, and every number in it can be traced to a packet. The specification sets no completion time for a command, so "expected time" on this page always means the usual time of the same command in this capture, next to the host's limit; both are named as such.

"Partition" in your words: the pieces of a transfer

A Read of 32 blocks is moved in several packets, each to one 4 KB page of host memory (the PRP entries of the command). The page calls each packet a piece and shows, per piece, the packet number, the LBA it starts at (from the page's position in the PRP list), the bytes, the time since the fetch, and the errors on that packet. So "is there a link-layer problem with this part of the command" is answered per piece. For a trim, the pieces are the LBA ranges in its list. A disk partition (C:, D:) is not on the wire; only namespaces and LBAs are.

What the NVMe specification says about time, and what it does not

  • It sets budgets for the controller: ready after enable within CAP.TO (500 ms units) or CRTO, resume from RTD3 within RTD3R, enter RTD3 within RTD3E, power-state entry and exit within ENLAT and EXLAT. Those are checked by stage 1 rules and listed on the page under "controller-level events that are not commands".
  • It sets no limit for a command. The Read command's DSM field carries an "access latency" hint (none, idle, normal, low), which is advice from the host to the drive, not a promise. The page shows the hint as a parameter and never uses it as a label.
  • The limits a host really applies come from its driver: Linux gives an I/O command 30 s and an admin command 60 s before it aborts and resets; Format, Sanitize and firmware commands get longer. The page names that source next to every "over the host's limit".

The other tables on the page

Command interval buckets (time between two submissions on the same queue), the host gap after a completion (the host's own think time, which the host owns in the queue model), queue depth at submission, transfer-size buckets, and latency buckets in 10 µs steps. The bucket edges are the ones in the driver team's Trace Vision tables, so the two tools can be compared side by side. "Download every command as a CSV file" gives one row per command with every step time, for the driver team's own analysis.
