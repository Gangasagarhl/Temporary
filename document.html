SSD failure analysis: from files in a folder to a test script

When a solid-state drive (SSD) fails, an engineer must find out why, and must be able to make the failure happen again. Today that means reading very large recordings by hand. This system reads the recording, finds the errors with fixed code, and produces a test script that replays the failure. AI agents do the drafting, so less human work is needed. A named person, the admin, approves every important step. AI reduces human work here; it does not replace the admin.

Be aware. Every recording on this machine is synthetic. None came from a real drive or from the field. No real drive has run a generated test: they ran on a simulated drive. The scorecard at the end says what that means for each claim.

1. System architecture

Input is only CSV files. Three families of agents work under the admin. Program code joins the files and finds the errors. Everything approved is stored and used again next time.

AI agentProgram codeAdminBoth AI and codeStored records

2. Stage 1: identifying the errors

Three families, in order. Each family ends at an admin's review. Family 1 learns each CSV file, giving a data dictionary. Family 2 joins the five files into one tree by identity keys. Family 3 turns the admin's questions and error definitions into rules, and code finds the errors. AI drafts and explains; it never decides whether an error exists, and it does not name the defect or decide its cause.

A note on names. In the application's own screens, “stage 1” means the isolation of one error's defect, and “stage 2” the procedural graph: its cause and its solution; the test case follows. This page uses the owner's wider framing: Stage 1 is everything up to the errors found; Stage 2 is from each error to its test script.

3. Stage 2: from the error to a test script

Each error is taken through its own page. Code computes the error's evidence card from its own command and decides its cause by fixed rules in a fixed order; the isolation is kept per error. The dictionary names the defect. The procedural graph holds, for each defect, its causes and their solutions. The admin judges stored solutions with one of four signals, and the judgements decide the order shown next time. The admin checks what a correct drive must answer and approves the test.

4. How the system improves itself

“Recursive self-improvement” has a specific meaning here. Approved dictionaries, strategies, rules, and defects with their causes and solutions are stored, versioned and used again. The admin's corrections change what happens next time. No model is trained or fine-tuned.

The admin's approval gates. Approve stores the work as a new version and moves on. Change runs the step again with the admin's comment. Reject stops the run. Ask questions the agent, without changing the state.

7. What stays human

  • The admin gives the data and the definitions of what counts as an error.
  • The admin approves every data dictionary, strategy, rule and piece of generated code before it is used.
  • The admin decides each error's cause (fixed rules propose one) and judges each stored solution with one of four signals.
  • The admin checks what a correct drive must answer, before any test is written, and approves each test file after its trial on the simulated drive.
  • The admin decides. AI drafts and explains. Program code finds the errors, computes each error's evidence and names the defect from the dictionary. The AI model never decides whether an error exists, what the defect is called, or its cause.
