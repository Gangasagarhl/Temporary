1The problem the project must solve

Why this part is here: The statement starts by naming the problems. Each card shows how the program solves one of them.

1.1

Find each fault, and say exactly where it starts and which side caused it

Done and checked

The statement says: effectively isolating defects

What we built
  • Stage 1 is the checker program. It reads the recording one line at a time.
  • It runs 167 checks on the packets and joins the broken checks into problems.
  • For each problem it gives the first wrong packet, the lines it covers, and which side caused it. It also names the matching entry in the list of 485 known errors.
  • Each problem gets one word: Confirmed, Suspect, or Needs evidence.
How we know it works
  • Our generator made a 4 GB test recording with 20.7 million lines. It placed 485 errors in it on purpose.
  • The checker found 437 of them from the packets alone, and 483 when the computer's logs were added.
  • It raised 0 false alarms. It opened 544 problems.
  • The same result came out again from the package that can be sent by mail, in 310 seconds.
For engineers: where to look, and the technical names

Code: stage1/pcie_isolate. Screens: app steps 2 and 3. Explained in HOW_DEFECTS_ARE_DETECTED.html and sections 3 to 5 of FINAL_WORKFLOW_AND_ALGORITHMS.html. Re-run proof: VERIFICATION_FROM_SCRATCH.md.

1.2

Make the fault happen again in the lab, quickly

Done, practice set-up only

The statement says: faster reproduction in lab environments

What we built
  • Stage 2 makes a found fault happen again on purpose.
  • If the fault was seen before, its saved steps are run first. That needs no search at all.
  • A new fault starts a search from the AI's plan. One search may make up to 300 tries.
  • If that finds nothing, it searches once more from the chapter's standard plan. That is up to 600 tries in all.
  • Everything must fit inside 10 minutes.
How we know it works
  • A fault seen before needed 0 search tries. A new fault needed 37 to 242 tries.
  • In a test with 30 hidden causes, the search found 28 within 600 tries. Random tries found only 3.
What is still missing
  • It has only been tried on the practice set-up, not on a real SSD.
For engineers: where to look, and the technical names

Code: stage2/stage2_v3.py, retrieval_v3.py. Running saved steps first is the "regression guard"; the chapter's standard plan is the "family template". Sections 7 and 9 of FINAL_WORKFLOW_AND_ALGORITHMS.html. The 28 of 30 result: documentation/research_and_reports/REPORT_final_implementation.md section 3 (same file as Database_Implmentation/claude_research_report/REPORT_final_implementation.md).

1.4

Look for weak spots before they fail in use

Done, practice set-up only

The statement says: proactive vulnerability analysis

What we built
  • A button called "Sweep the neighbourhood". It starts from the steps that make the fault happen.
  • Then it changes them a little. Each time setting is tried at half and at double. Every other power state is tried. A burst of commands is made twice as long. That gives up to 15 changed versions.
  • If the lab machine can break packets on purpose, that is tried too.
  • Versions that still bring the fault out are the weak spots. The strongest ones become repeat tests.
  • A second button, "Generate test case", makes versions that reach the fault in a different way.
  • When the fixed firmware is checked, a similar but different error is added on purpose. The test must not mix the two up.
How we know it works
  • Check B10 of the live run and check U25 of the screen test passed.
What is still missing
  • Tried only on the practice set-up.
  • Breaking packets on purpose needs a real lab machine that offers it. On the practice set-up those versions are marked "hardware bench only".
For engineers: where to look, and the technical names

Code: stage2/sweep.py, stage2_v3._sweep, stage2/compose.py. Packets broken on purpose are "jammer" faults; the lab machine must offer inject(spec) and clear_faults() in app/bench_hook.py. The similar error added on purpose is the "decoy". Sections 10.1 and 10.2 of FINAL_WORKFLOW_AND_ALGORITHMS.html.

2.2

A search that learns by trying starts from the AI's plan, and keeps changing the commands and their timing

Done and checked

The statement says: RL agent uses the LLM's scenario as a seed to iteratively optimize command sequences and timing parameters

What we built
  • The search starts from the AI's plan. It also uses the saved steps, earlier examples from the same chapter, and the chapter's standard plan.
  • Each try changes something. It adds, removes, swaps, replaces or repeats a command. It changes a time a little. Or it mixes two good tries.
  • When a try works, it is run again several times to be sure it was not luck.
  • Then the steps are cut down to the fewest that still work.
  • There are two ways to choose the next change. The default picks the kind of change that has worked best so far. The other (PPO) learns a small choosing rule during the search. PPO is the one named in the drawing.
How we know it works
  • Both ways were tried 24 times on the practice SSD model, with the same starting numbers.
  • PPO succeeded 15 times, using 166 tries in the middle case. The default succeeded 14 times, using 156 tries.

Neither way trains an AI model. The default stays on because it needs no tuning. Switching to PPO is one line in the settings.

For engineers: where to look, and the technical names

Code: stage2/optimizer.py, stage2/ppo_optimizer.py; setting config/app_config.json → stage2.optimizer. Methods: the default is a bandit with Thompson sampling and Go-Explore restarts; PPO is a clipped-surrogate policy gradient with GAE; the "run again to be sure" step is a Wilson lower bound; cutting down the steps is ddmin. Results: stage2/bench_optimizers_result.json. Section 9 of FINAL_WORKFLOW_AND_ALGORITHMS.html; PROVENANCE_AUDIT.md section 4.

2.3

Done and checked

What we built

How we know it works

3.1What the explained statement asks for that this package does not do

Why this part is here: the explained statement asks for more than the program does. This list says it plainly, so nobody thinks it is done.

The two Windows start-up runs in the statement are not processedThe statement's example has two ADK runs on the same firmware: one failed (14.948 s) and one passed (13.206 s), with 106 GB of the drive in use. There is no raw ADK log in this package. The only sample is a ready-made result file (data/samples/adk_stage1_sample.json).
A passing run is not used as the thing to compare againstFor ADK, whatever boot_etl worked out is simply brought in. For PCIe recordings, the checker compares with the rule books and with what is normal in the same recording.
Sudden jumps in the measured numbers are passed on, not usedMoments where a measured number jumps (change points) go into the message to the AI and into the test's notes. They are not ranked or tested.
The search cannot change how full the drive isThe search can change five settings: the gap between commands, the commands in one burst, the rest time, the commands waiting at once, and the block size. It can also choose from 12 NVMe commands and 5 power states. It has no setting for how full the drive is, or for how free-space commands (trim) line up.
Two buttons are off for work-run faults"Sweep the neighbourhood" and "Generate test case" are switched off for ADK and PCMark faults, until a real lab machine runs the work.
The work-run test is a different kind of testIt compares the measured number with the range seen in passing runs. It repeats 3 times. It skips itself when there is no hardware. The "above 0.9, three times" rule is not checked for it.

8.7

The loop for the best settings: above 0.9, three times in a row, is best. More than 10 minutes is a fail.

Done, practice set-up only

The statement says: Loop for best params: test score > 0.9 three times consecutively = optimal; > 10 min (first-level triage) = fail

What we built
  • Each lab run gets a score made of three yes/no checks. Was the same error found? Did the same first check break? Was it Confirmed, not just Suspect?
  • The score is the number of yes answers out of 3. Only 3 out of 3 is above 0.9.
  • So "best" means: the same error, found by the same first check, confirmed, in three lab runs in a row.
  • Each search may take at most 10 minutes. Then the search stops, but the lab check still finishes. The 10-minute limit is also reported for every stage 1 run.
  • Inside the search, a try is only accepted when it repeats often enough in 8 more runs.
What is still missing
  • Tried only on the practice set-up.
  • Neither rule is checked for ADK or PCMark faults, because the practice set-up cannot run a Windows work run.
For engineers: where to look, and the technical names

Constants in stage2/loop_rules.py: SCORE_THRESHOLD 0.9, OPTIMAL_CONSECUTIVE 3, FIRST_LEVEL_TRIAGE_S 600. The search stop is a Wilson 95 % lower bound of at least 0.5. Status when the time runs out: triage_timeout.

?What the words mean

Why this part is here: so you can look up any word on this page without leaving it.

The statement
The short table, written by the person who set the project, that says what must be built.
The checker
Our program that reads the recording and finds faults. Stage 1. The app screens call it "the analyser".
Recording
The table file (CSV) that a capture tool saves. One line is one packet that went over the wire between the computer and the SSD.
Fault
Something that went wrong. The app screens call it a defect.
Error list
The list of 485 known errors, in ten chapters. The app screens call it the catalogue.
AI reviewer
An AI program that reads the same packets as the checker and says agree, disagree or not sure. It also writes first plans.
Search
Stage 2's program that tries many small changes to the steps, to make the fault happen again.
Lab check
The steps run on the lab machine. Then the same checker must find the same fault again in the new recording.
Practice set-up
A lab test machine made of software. It pretends to be an SSD with a hidden fault. It is used until a real lab machine is connected.
Repeat test
A test that is run again later, to make sure an old fault has not come back. Also called a regression test.
Firmware
The program inside the SSD. Faulty firmware has the fault. Fixed firmware should not.
Knowledge base
The saved record of every fault, the steps that made it happen again, its tests, and every admin decision.
Fingerprint
The details that tell one fault apart from all others.
Admin
The person who checks each suggestion and presses Correct, Not correct, or another button.
Key result
A number the project promised to measure. Also called a KPI.
