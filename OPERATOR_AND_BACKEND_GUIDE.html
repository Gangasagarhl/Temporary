1. The problem and the answer in one picture

The problem. Sometimes a solid-state drive (a storage drive with no moving parts) goes wrong in real use, away from the lab. Then engineers record the traffic between the computer and the drive. They use a measuring tool called an analyzer. It records every packet (small bundle of data) on the cable. This recording is called a trace. It is saved as a CSV file (a plain text table). One trace can hold millions of packets. Today a person reads it by hand and finds the defect (the fault). Next they guess how to make it happen again in the lab. They keep trying until it does. Then they write a test script, so the defect can never come back without anyone noticing. This takes days, and it depends on one expert.

The answer. This app does those four jobs. But a person stays in charge of every decision:

  1. Stage 1, the analyser (the checking program), reads the trace one packet at a time. It uses fixed rules taken from two official rule books. One is for PCIe (the fast link that joins the drive to the computer). The other is for NVMe (the set of rules the computer uses to talk to the drive). The analyser groups the rules that fired (found a problem) into defects. It matches each defect to one entry in a list of 485 known error types. An AI model gives a second opinion on each defect. The screens call it the AI reviewer. But the rules always win.
  2. Stage 2, making it happen again, looks up each defect in the knowledge base (the program's memory of earlier decisions). It shows the procedure (list of steps) that worked before. Next to it, it shows a new suggestion from the AI reviewer. Then an admin (the engineer who decides) makes the choice.
  3. The lab runs the chosen procedure on the drive. Maybe the defect does not happen. Then a search changes the commands and timing until it does. Next, the program finds the hardest timing that still sets off the defect. These are the most stressful conditions.
  4. The lab check runs the procedure on two kinds of firmware (the program inside the drive). On the firmware known to be bad, the defect must appear. On the fixed firmware, it must not appear. Only then does the program save it as a regression test that a computer can run. A regression test is a test that runs again on every new firmware. So the defect cannot quietly come back.

The knowledge base stores every decision the admin makes as an event (an entry in its diary of changes). Each one changes the numbers that decide what is shown first next time. That is the learning loop. No AI model is trained or retrained anywhere. The learning is just counting. It uses simple maths, shown in section 10.

The whole flow

2. Every abbreviation and special word, written out

The screens use plain words wherever they can. But a few places still use the official names from the official rule books. These places are the packet rows, the evidence and the AI reviewer's text. The AI reviewer is an AI model asked for a second opinion. These places keep the official names because engineers search for those names. This section explains every one of them. The words are grouped by topic. To jump to a word, use your browser's find box (Ctrl+F).

2.1 The link between computer and drive (PCIe)

WordWritten outWhat it means here
PCIePeripheral Component Interconnect Express (a fast way to plug extra parts into a computer)The fast link that joins the drive to the computer. It is one shared set of rules for the slot, the wires and the talking. Think of it as a road between two towns. Everything in the trace travelled along this road.
Host / Root Complex (RC) / root port—The computer's end of the link. "Downstream" means going from the host to the drive.
Device / endpoint / SSDSolid-State Drive (a storage drive with no moving parts)The drive's end of the link. "Upstream" means going from the drive to the host.
Analyzer / trace / capture—The analyzer is a tool that records every packet on the link. Two makers of such tools are LeCroy and VIAVI. The trace, or capture, is the recording it makes. It is like a camera by the road that films every car. The app reads the saved recording as a CSV file. That file has 113 columns and one row per packet.
CSVComma-Separated ValuesA text file that holds a table. Each line is one row. Commas split each row into columns. The analyzer saves its recording in this form.
TLPTransaction Layer Packet (a packet that does a job)A packet that carries real work. The work can be a read, a write, a read or write of the device's settings area, or an answer. A packet is like a letter in an envelope. The address is on the outside, and the content is inside. Most evidence is TLPs.
MRd / MWrMemory Read / Memory Write requestA TLP that reads from or writes to an address. "MRd(32)" means the address is 32 bits long. The host uses them to read the drive's registers. Registers are small numbered slots inside a chip that hold settings or status. The drive uses these TLPs to fetch commands and move data.
Cpl / CplDCompletion / Completion with DataThe answer to a read, or to a request to the settings area. It carries a status, a short result code. The next four rows list the codes:
SCSuccessful CompletionThe request worked.
URUnsupported Request (a request it cannot do)The receiver said no to the request. For example, the address was not valid, or the device was not ready.
CACompleter Abort (the one answering gave up)The receiver tried to do the request, but failed while doing it.
CRSConfiguration Request Retry Status (try your settings request again)It means "Not ready yet, ask again". It is allowed only for settings reads, soon after a reset (a restart).
CfgRd0 / CfgWr0Configuration Read / Write, type 0Reads or writes of the device's configuration space. That is the settings area every PCIe device has. It holds standard registers. They say who the device is, which power state it is in, and what it can do.
Configuration space, register 0x044 …—Configuration space is a row of numbered registers, like numbered lockers in a hallway. "0x" means the number is written in base 16 (hexadecimal). Base 16 uses the digits 0 to 9 and then A to F. In the example, register 0x044 is the register that controls power saving.
BARBase Address Register (the register that holds a starting address)A register in the settings area. It tells the host at which memory address it can reach the drive's own registers. It is like a house number that tells you where to knock.
MMIOMemory-Mapped Input/Output (talking to a device through memory addresses)Reading or writing the drive's registers as if they were normal memory. The host uses the address from the BAR. "MMIO read 0x1C" means a read of the drive's register at offset 0x1C. The offset is the distance from that starting address.
DLLPData Link Layer PacketSmall packets that keep one link tidy and running. They travel only between the two ends of one link. Examples are "got it" receipts and credits. They carry no real work.
ACK / NAKAcknowledge / Negative Acknowledge ("got it" / "not got it right")DLLPs that answer each TLP. ACK says "it arrived whole". NAK says "please send it again". They work like a signed delivery slip. The packet picture shows them in grey.
PSN / AckNak Seq NumPacket Sequence Number (the packet's place in line)The number each TLP gets on one link. ACK and NAK use it to say which packet they mean. It works like a ticket number at a shop counter.
LCRC / ECRCLink / End-to-end Cyclic Redundancy CheckCheck numbers that catch broken packets. The sender works out a number from the packet's content and adds it. The receiver works it out again. If the two numbers differ, the packet was damaged. LCRC checks one link. ECRC checks the whole way, from one end to the other.
Replay—The sender sends a TLP again. It does this after a NAK, or after waiting too long (a timeout).
Flow control, credits, UpdateFC—Each side tells the other how much waiting room (buffer space) it has. These amounts are called "credits". Think of free seats in a waiting room. UpdateFC is the DLLP that hands credits back when seats free up. A credit stall means the sender must wait, because no credits come back.
Tag / Requester ID—Numbers that tie each answer (completion) to the request it answers. They work like a cloakroom ticket that matches your coat. A Requester ID is written as bus:device.function, for example 002:00:0.
Ordered set, LTSSM, Recovery, L0Link Training and Status State Machine (the steps a link goes through to start and keep working)Ordered sets are special control signals sent on the wires. The LTSSM is the list of steps that trains the link. Training means the two ends agree how to talk. L0 is the normal working state. Recovery means the link trains again after errors.
AER, ERR_COR, ERR_NONFATAL, ERR_FATALAdvanced Error Reporting; correctable / non-fatal / fatal error message (can be fixed / serious / very serious)The error messages a PCIe device sends to the host. They are sorted by how bad the error is.
MSI / MSI-XMessage Signalled Interrupt (extended)How the drive interrupts the host to get its attention. It writes to a special address, like a tap on the shoulder.
IOMMU / DMAInput/Output Memory Management Unit / Direct Memory AccessDMA means the drive reads or writes the host's memory by itself. The IOMMU is the host's guard. It blocks DMA to any address the drive was not given. Think of a guard who only lets you into the rooms on your pass.
Hot-unplug, surprise link down—The drive vanishes from the link without the normal switch-off steps. It is like pulling out a plug while the machine is running.
Jammer—A tool placed on the link that damages or delays packets on purpose. It tests how well the drive copes. It is optional. It is used only on a hardware bench (a real test table with a real drive).

2.2 The drive's command language (NVMe)

WordWritten outWhat it means here
NVMeNon-Volatile Memory Express (for memory that keeps its data when the power is off)The list of commands the host uses to talk to the drive over PCIe (read, write, flush, …). If PCIe is the road, NVMe is the language of the letters sent along it.
SQ / CQSubmission Queue / Completion Queue (the line of jobs handed in / the line of answers)Each queue is a ring of memory in the host. Picture a round tray with numbered places that is used again and again. The host puts commands in a submission queue. The drive puts answers in a completion queue.
SQE / CQESubmission / Completion Queue EntryOne place in a queue. An SQE holds one command (64 bytes). A CQE holds one answer (16 bytes).
SQID / CQID / CIDSubmission / Completion Queue ID, Command IDNumbers that say which queue and which command. The analyser (the checking program) follows a command by these numbers. It never uses the command's place in the file.
Doorbell—A drive register the host writes to say "new commands are in the queue". It works just like ringing a doorbell.
Phase bit—A bit (a single 0 or 1) in each CQE. It flips on every trip around the ring. That way the host can tell which answers are new.
PRP / SGLPhysical Region Page / Scatter-Gather List (two kinds of lists that say where the data is)The two ways a command tells the drive where the data sits in host memory. Both work like a list of addresses for picking up parcels.
Admin queue / I/O queue—Queue 0 is the admin queue. It carries commands that manage the drive (Identify, Get Log Page …). The other queues carry reads and writes. I/O means input and output.
CC / CSTSController Configuration / Controller Status register (the drive's on switch / the drive's status light)Two drive registers. The host turns the drive on with CC.EN. It checks whether the drive is ready with CSTS.RDY. "CSTS reads all-ones" (0xFFFFFFFF) means the drive no longer answers.
Identify Controller (CNS 01h)Controller or Namespace Structure 01hAn admin command. Its answer holds the drive's model number, serial number and firmware version. Firmware is the drive's own built-in software. The analyser takes the device name from this answer.
VID / DID / SSVIDVendor ID / Device ID / Subsystem Vendor ID (maker number / product number / maker number of the finished board)Numbers for the maker and the product. They sit at the top of the PCIe settings area (the configuration header). The analyser uses them for the device name when the trace has no Identify answer.
SN / MN / FRSerial Number / Model Number / Firmware RevisionParts (fields) of the Identify answer.
Namespace, nsze, LBANamespace Size, Logical Block AddressA namespace is one part of the drive, like one shelf in a bookcase. nsze is its size in blocks. An LBA is a block number, like a page number in a book. With nsze, the analyser can tell a read past the end from a valid read.
Flush / FUA— / Force Unit Access (write it to the flash now)A command (Flush) or a flag (FUA) that forces written data onto the flash memory. Then the data stays safe even if the power fails.
Trim (Deallocate), Write Zeroes—Trim tells the drive that some blocks are no longer needed. Write Zeroes tells the drive that some blocks should read as zero.
Get Log Page, Set Features, Abort, SMARTSelf-Monitoring, Analysis and Reporting Technology (the drive's own health check)Admin commands. Get Log Page reads a log, for example the SMART health log. Set Features changes a setting. Abort cancels a command.
AER (NVMe)Asynchronous Event Request (a request that is answered later, whenever something happens)A command the drive answers only when something happens, such as a warning or a log change. It is like asking a friend to call you when your parcel arrives.
Controller reset, power cycle—A controller reset restarts the drive's controller (CC.EN 1→0→1). The controller is the drive's small brain. A power cycle switches the power off and on again.
Queue depth (QD)—How many commands are waiting for an answer at the same time. It is one of the five timing values of a procedure (a recipe for making the fault happen again).
Block size (KB)kilobytes (about a thousand bytes each)The size of each read or write.
Burst length—How many commands are sent one right after another, before a pause.
Between commands (µs) / idle gap (ms)microseconds (millionths of a second) / milliseconds (thousandths)The gap between two commands, and the quiet time before the whole list of commands starts.
dmesg -x—The Linux kernel log. The kernel is the heart of Linux. Each line has a level that shows how serious it is. This log is host evidence. It helps with defects that leave no trace on the link.
host_events.jsonl—Records written by tools on the host, one JSON object (one record) per line. This is also host evidence.
fio, nvme-cli, SPDK—Common Linux tools. A hardware bench uses them to send the commands of a procedure to a real drive.

2.3 Power-saving words

WordWritten outWhat it means here
D0 / D3hotDevice power state 0 / 3 (hot)D0 means fully on. D3hot means deep sleep, with the power still connected. After D3hot→D0, the device needs time to wake up. The official PCI Power Management rule book says software must wait 10 ms before using the device. Error type T-42 is a host that does not wait. It is like talking to someone before they are fully awake.
PMCSRPower Management Control/Status RegisterThe register in the settings area (here 0x044) that the host writes to change the D-state. "DATA 03" means D3hot. "DATA 00" means D0.
ASPM, L1, L1.2Active State Power ManagementThe link itself (not the device) goes to sleep when nothing is happening. L1 and L1.2 are deeper sleep states of the link. "ASPM idle" in a procedure means: wait, so the link falls into such a sleep state.
APSTAutonomous Power State Transition (the drive changes its power state by itself)The drive changes its own NVMe power state after it has been idle for a while. It is like a phone that dims its screen when you stop using it.
PME, LTRPower Management Event / Latency Tolerance Reporting (wake-up message / how much delay is fine)PME is a wake-up message. LTR tells how long the device can put up with waiting.

2.5 Words of stage 1 (the analyser)

WordWhat it means
FindingOne rule going off on one packet, like one smoke alarm beeping. A trace can give thousands of findings. The analyser groups them into defects.
Defect (incident)A group of findings tied together by a shared identifier (the same transaction, command or sequence number), by a reference (one finding points at the packet of another) or by the same packet. Findings with no identifier are counted as a series of their kind. Each defect has one "first abnormal packet", one root cause and one catalogue match.
First abnormal packetThe earliest packet where things stop being normal. It is not always the loudest one. Think of the first domino that falls, not the biggest crash. The packet picture marks it "first abnormal" in red.
Root cause / knock-on effect / separate findingThe three jobs a finding can have in one defect. The root cause is the first cause. A knock-on effect is something the root cause led to, like the dominoes that fall after the first. A separate finding is related, but it does not come from the root cause.
Confirmed / Suspect / Needs evidenceThe analyser's verdict (its decision). Confirmed = the rules prove it from the packets. Suspect = a rule went off, but the proof is not complete. Needs evidence = the packets show only a sign of the problem. A host log would be needed.
AI reviewer agrees / not sure / disagreesThe AI reviewer's second opinion on the analyser's verdict. It reads the same rows and the rule text. It never changes the verdict.
Fresh model call / verdict reused from the cacheFresh = the AI reviewer was asked just now. Reused = an earlier run already confirmed the same pattern. The same pattern means the same error type, first rule, family and layer. The order of packet kinds must match too. So must the model and the prompt (the question text). Then the app uses the stored answer and makes no model call. The cache is the store of earlier answers.
Isolation statusThe final word for each defect. It says whether the fault was found and pinned down. The defect page shows it as a badge: Confirmed, Suspect or Needs evidence, with one sentence that explains it. Behind the badge are five values. isolated (badge Confirmed): the rules and the AI reviewer agree. isolated from the packets alone (badge Confirmed): no AI reviewer ran. needs outside evidence (badge Needs evidence): the packets alone cannot prove it. disputed (badge Suspect): the AI reviewer disagreed, so check by hand. synthesised (badge Confirmed): made-up demo data only.
LayerWhere in the stack the defect sits. The stack is the pile of layers that work together, from the wires up to the commands. The layers are: physical link, data link, transaction, configuration, NVMe command, power management, host, sideband, statistics, the capture itself.
Failure signatureThe unique mark of a defect that stage 2 uses. It is made from the error type, the first rule, the layer and the timing class. It also holds the link events. And it holds the packet kinds just before the "first abnormal packet". Two defects with the same signature count as "the same defect".

2.6 Words of stage 2 (making the fault happen again)

WordWhat it means
Knowledge baseThe program's memory of earlier decisions. It is the database db/knowledge.sqlite. It starts empty. Only events fill it: decisions, lab results and test files.
CauseA saved reason why an error type happens. Each error type has at least one. Inside the database, the first one is called "c0".
Procedure (scenario, solution)A recipe to make a defect happen again in the lab. It has three parts. First, a list of up to 12 commands in order, picked from the 12 the bench can send. Second, five timing values: queue depth, gap between commands, block size, burst length and idle gap. Third, a power state. Its id, such as procedure #074e18b2, is the first 8 characters of a hash of its contents. A hash is a short unique mark worked out from the contents. So the same recipe always has the same id.
Saved procedureA procedure kept in the knowledge base for this error type.
AI reviewer's proposalA procedure that the AI reviewer suggests now, from the packets of this defect. Nobody has run it yet.
Procedure statusIt starts as proposed: written, but not run. Then the lab runs it. If it made the defect happen again: validated in the lab, awaiting approval by a second admin. If it did not: failed validation. Next comes approved by a second admin. Later it can be replaced by a newer version or retired (no longer used).
Seen before: YES / related / NOThe answer of the lookup (the search of the knowledge base). YES = same error type, same device and firmware, and a strong match. Related = same error type or family, but a different situation. NO = nothing like it is stored.
Lab runOne run of a procedure on the device. After it, the same analyser checks the new trace. On this laptop the device is a pretend one, made by software (see 9.6). On a real bench it is the real drive.
Known-bad / fixed firmwareKnown-bad firmware is the drive software where the defect was seen. Fixed firmware is the corrected version. A good test fails on the first and passes on the second.
Lab check (closed loop)The procedure runs 6 times on known-bad firmware and 3 times on fixed firmware. Only one result makes it a regression test. The defect must show up at least once on known-bad, and never on fixed.
Reproduced in at least 68 % of lab runsA careful, low guess of how often the procedure sets off the defect. It is the 95 % confidence lower bound (section 10.5). We can be 95 % sure the true rate is at least this high. "Likely" = at least 50 %. "very likely" = at least 80 %.
Score per lab run, optimalEach lab run gets 3 yes/no checks. Was the same error type found? Was it found by the same first rule? Was the verdict Confirmed? Score = checks passed / 3. Optimal = score above 0.9 (all three) in 3 lab runs in a row. This rule comes from the project's drawing of how its parts fit together.
First-level triage limitTriage means a quick first sort of problems, like a nurse who decides who is seen first. The limit is 10 minutes per defect. If the search and the lab check take longer, the try counts as failed.
Most stressful conditionsFirst, the defect must be made to happen again, and this must be confirmed. Then the app pushes each timing value harder, step by step, while the defect still appears. It files the hardest version as a second test (section 9.4).
Failure-prone conditionsSmall changes to the working procedure that also set off the defect. You get them with the button "Try nearby variations".
Regression testA test that is run again after every change, to make sure the fault has not come back. Each one is a folder under suite/. The folder holds a pytest script, which is the test itself. It also holds a manifest.json. That file describes the procedure, the expected result and where the test came from. Last, conftest.py connects the test to the bench.
LessonA note in your own words, saved with an error type. The AI reviewer must read the lessons when it makes its next proposal for that error type.
Second admin, two-person ruleAn admin is the engineer who decides. Some actions need a second, different person. These are: approving a procedure, retiring a procedure and deleting a cause. The database says no to the change when both names are the same. It is like a bank safe that needs two keys.

5.2 The eight steps, and what each one does in the program

The job function run_stage1 runs the analyser's own commands, one after another. It reads the progress they print, and times each one.

  1. Read the capture and check every packet (analyze). The analyser goes through the CSV once, row by row. It never loads the whole file, so it works even on a 4 GB file. Each row goes to the code for its kind of packet. One kind is TLP (a packet that carries real work). Others are ACK (a "got it" reply) and other DLLPs (small housekeeping packets). Then come ordered sets (control signals on the cable), link events and markers. Fifteen trackers keep the state that the official rule book defines. They follow the link state and the ACK/NAK numbers (got it / send it again). They follow flow-control credits (how much room each side has left). They follow open requests by Requester ID + Tag (numbers that tie an answer to its request). They keep a copy of the standard setup registers every PCIe device has. They keep the BAR map (where the drive's registers sit in memory). They follow the drive's registers and the NVMe queues (NVMe is the drive's command language). They follow each command by queue + command id. They also follow interrupts (the drive's signals to the computer), power state, messages and speed counts. When a state goes wrong, a rule "fires". The analyser then records a finding with its packet number and a detail text. It always links packets by their id numbers, never by "the next row". Example: the rule that finds error type T-42. The host writes D0 (fully on) into the power-management register. The analyser notes the time. Any memory read or write to the drive less than 10 ms later fires CFG.D0_EARLY. The rule's line in the rule table gives its tier (what kind of check it is). It also gives its level (defect or context), the verdict it hands out, its layer and its families.
  2. Line up the host evidence with the packets (fuse). This step runs only when you gave a dmesg or host_events file. It places each host line on the same timeline as the packets. Then a defect can point to that line.
  3. Group the rules that fired into defects (isolate). Findings that name the same transaction, command or sequence number, or that refer to each other's packet, form one defect; nothing is joined by distance. A context finding (a host action, a reset) is added only when a finding refers to it. For each defect the step works out several things. First, the first packet that went wrong. Second, an evidence graph. This map links findings with the same ids, and adds published cause→effect links. The starting point of the map is the root cause. Third, the catalogue match. The step scores all 485 error types against the findings and keeps the top three as possible answers. Fourth, who caused it, found by rules R0–R10 (section 2.4). Last, the NVMe command and host task involved, and the packet rows around the defect.
  4. Summarise every NVMe command (commands). While reading, the analyser followed each command from its doorbell write to its completion entry and wrote one line per command (commands.jsonl). This step turns those lines into the NVMe commands page: the parameters each command carried (decoded as the NVMe specifications define the fields), the time of each step, a label with its basis, and the packet-level findings that carry the command's identity.
  5. Reuse AI reviewer verdicts from earlier runs (pattern cache, a store of earlier answers). For each defect the step builds a key from these things. The error type, the first rule, the family and the layer. The set of rules, and the order of packet kinds in its rows. The AI model, and the version of the prompt (the question sent to the AI). If that key was confirmed before, the step writes the stored verdict for this defect. It calls no model. A new model or a new prompt gives a new key. So old verdicts are never used for a new model.
  6. Ask the AI reviewer for a second opinion on each defect (review). This runs only for defects the cache did not answer, and only when a model is set up. The AI reviewer gets the evidence rows and the rule text. It must answer agrees, not sure or disagrees. It must also say which rules it agrees with and which packets it points to. It says who it thinks caused the defect, and gives other explanations. If it points to packets that are not in the evidence, the program flags them. It never changes the analyser's verdict.
  7. Write the stage 1 report (report). It writes isolation.json and isolation_report.md. They hold one record per defect: status, where, why and evidence. They also say what outside evidence is needed, and give the fix text from the catalogue.
  8. (Optional) Assess the capture as a whole (capture_check). One model call says if this capture can show what we are looking for at all. It is only advice; it never makes the run fail.

Why the AI reviewer is only a second opinion

The rules come from the official rule books, and anyone can check them. Nobody can check an AI answer that way. So the verdict comes from the rules. The AI reviewer's job is to catch a rule that fired for the wrong reason. The screen shows every disagreement ("disputed: inspect by hand"). The program never quietly acts on it.

5.3 The defect rows under the ring

Each row shows Defect N and the error type written out. Next comes the verdict badge (✓ Confirmed ? Suspect ! Needs evidence). Then the AI reviewer badge, whether the verdict came from the cache, and the packet range. When you open the row, you see more. It shows the error family and the layer. It shows the first packet that went wrong (on the screen: "first abnormal packet"). It shows the rule that fired there, with its detail ("MMIO read 0x1C 2.000 ms after D3hot→D0"). 7.6 Generate test cases from the knowledge base

Text on the screen: "The database holds 5 correct / optimised sequences (saved procedures) for this error type. The AI reviewer composes up to three test variants from them that recreate the defect — a robust recreation, the same trigger at its timing boundary, and a different path to the same state. Each variant is run in the lab, kept only if the analyser finds this defect, and filed as a regression test that names its sources and why. Nothing is approved automatically."

Why it matters: one way of making the defect happen gives one test. But a defect usually has more than one way in. Some tests only play back the exact sequence seen in real use. Such a test can pass a fix that covers only that one path. Composing (building new tests from parts that worked) turns the knowledge already earned into a small family of tests. That knowledge is the procedures that worked. It costs no extra search.

What happens (action compose_tests, Stage2V3._compose): the program collects the saved procedures of this error type, and of its family, as sources. The AI reviewer gets them, with the evidence and the lessons. It must send back up to three variants. Each variant has a name, a reason, the packets it expects, and the sources it used. Code cleans each variant. Each one runs 6 times. If none makes the defect happen, the search starts from the best one. Each variant that works goes through the lab check. It is then filed as a test. The test's list of contents (its manifest) names its sources, the model that composed it, and why. Filed variants are "awaiting approval by a second admin". The button is switched off when nothing is saved for this error type. The result lists each variant with its lab numbers and test script.

7.7 Failure-prone conditions — try nearby variations

Text on the screen: "Around the reproducing procedure, each timing value is tried at half and at double, every other power state, a doubled burst, and injected link faults when the bench can inject them. Variations that still reproduce the defect are the failure-prone conditions; the most stressful ones are filed as regression tests (never approved automatically)."

Why it matters: the project statement asks for "proactive vulnerability analysis" of the "surrounding failure-prone areas". That means looking ahead for weak spots near the fault. A firmware fix may only move the edge a little. Then it would pass the first test but fail a close neighbour. These variations map how wide the failing area is.

What happens (action sweep, Stage2V3._sweep and stage2/sweep.py): the program starts from the best saved procedure. It builds up to 15 variations, and each one changes one thing. It tries each of the five timing values at ×0.5 and ×2, inside the lab ranges. It adds an idle gap of 500 ms if there was none. It tries each other power state. It repeats the last command. With a hardware jammer (a box that disturbs the link on purpose), it adds three link faults. Each variation runs 3 times. If the defect shows in at least 2 of 3 runs, the variation is failure-prone. They are put in order by how many runs showed the defect. Ties go to the one that pushes the value furthest (stress_of). That is how many times bigger the changed value is. A power-state change or a jammer fault counts as 2. A longer list of commands counts as 1.5. The top 3 go through the lab check and are filed. The result table has the columns Variation, Reproduced (lab runs), Failure-prone, How far it was pushed, and Regression test filed.

"Preview as it will be saved" shows the result and the number of changes. The editor refuses values outside the ranges. Propose my procedure and run it on the device sends add_procedure.

These options are everything the bench can do, not fixed recipes

The twelve commands are every command the lab bench can send. The five timing values and the power state are the knobs it can set. You may put them together in any order, up to twelve steps. The search of section 9 changes exactly the same things. Some commands could destroy the drive: format, sanitize, firmware download or commit, and namespace delete. They are not in the list, and the search refuses them.

Chips at the top show the total number of decisions, the positive ones and the negative ones. The table has the columns When, Who, Decision, Reason or note and Lab outcome. When shows the date and time, then "#" and the event number. You need that number for Undo. In Decision, + green = positive, − red = negative, grey = neutral. Negative = Reject, Could not be reproduced, Dispute, Retire, deletion, and a lesson that starts with "NOT CORRECT". Everything else is neutral. 9. What happens in the lab when you press Correct

Seven decisions send work to the lab. Four of them are Accept, Accept with a note, Add a cause, and Add a procedure (also "Save corrected version"). The other three are Generate test cases, Try nearby variations and Restart the search. This section follows Correct from the click to the test file.

9.1 The start: your decision, then the choice of way

9.2 Way 1: reuse the saved procedure (the regression guard)

Say you accepted a procedure saved for this same error type. The lab first runs it 6 times. If the defect still shows in at least 3 of the 6 runs, the lab reuses it. Then there is no search and no call to the AI reviewer. The lab check comes next. This is the biggest time saving the knowledge base brings. The second time a defect is seen, making it happen again takes seconds. Sometimes the saved procedure no longer works, for example on a new device or new firmware. Then a lesson records that, and the search starts from that procedure.

9.3 Way 2: the search (the "reinforcement-learning agent" of the project statement)

The seed (the starting point). The program asks the AI reviewer for a procedure. With the question, it sends the evidence and the rule text. It also sends the saved procedure, if there is one. It adds up to a few approved procedures of the same family as examples. Last, it adds the lessons for this error type. Then the program cleans the answer. It removes unknown commands and pulls timing values back inside their limits. It checks the packets that the answer points to. Right after that, the lab also tries the saved procedure, two examples and the family's known trigger shape.

The search loop (Optimizer.search in stage2/optimizer.py). Each try makes one change to the current procedure. There are 14 kinds of change. It can add, remove, replace or repeat a command, or swap two commands. It can change the queue depth, block size, spacing, burst, idle gap or power state. It can combine two procedures. It can take a small step on one timing value. Or it can jump one timing value to a standard point. Thompson sampling picks which kind of change to use. It is a lucky draw where each kind's own tally of successes sets its odds. So the kinds of change that helped before get picked more often. The lab runs the new procedure and gives it a reward (points). The reward has two parts that are added together. First, a ladder shows how far the defect got. On it, 0 = nothing and 1 = the family's pattern appeared. 2 = almost all conditions met, and 3–4 = the defect happened again. Second, a value from 0 to 1 shows how close each condition came. The search keeps a change that is at least as good as before. After 25 tries with no gain, the search jumps back to a promising earlier procedure. It keeps these in an archive, one for each different shape (the Go-Explore idea). Say the AI reviewer is set up and the search is stuck. Then the program may ask it for a fresh proposal, up to 3 times. When a procedure makes the defect happen, 8 more runs confirm it. Let k be the number of those 8 runs that showed the defect. The procedure counts as reproduced when the Wilson lower bound of k of 8 is at least 0.5. That needs 7 of 8 (section 10.5 explains the bound). Limits: 300 tries and the 10-minute triage limit. Learning from rewards like this is what "reinforcement learning" means.

9.4 Shorten it, then push it to its limits

Shorten (minimize, the ddmin idea: cut away one part at a time). The program removes each command in turn. It also sets each timing value back to its default. It keeps a change when the defect still appears in 2 of 3 runs. The result is the shortest, plainest procedure that still sets off the defect. An engineer can understand it most easily, and a test can run it most easily.

Most stressful conditions (stress_ascent). This step was added on 27 October 2026. It meets these words of the statement: "the most stressful trigger conditions are converted into executable test scripts". It starts from the confirmed, shortened procedure. It pushes each timing value one step toward what a drive is least likely to survive. Commands come twice as close together. The step doubles queue depth, burst length, block size and idle gap. It keeps a step only when the defect still appears in 2 of 3 runs. The loop repeats until nothing can be pushed further, or until 30 lab runs are used. The hardest version that still sets off the defect goes through the same lab check. It is then filed as a second test. The first test guards the point where the defect was seen. The second test guards the space around that point. So a fix must hold even under the harshest timing at which the drive was seen to fail. This step runs after a search and after a reused saved procedure. It also runs after your own version made the defect happen again.

9.5 The lab check and the score

The lab runs the procedure 6 times on the known-bad firmware (the firmware that has the fault). Then it runs it 3 times on the fixed firmware. After every run, the same stage-1 analyser reads the new trace. So the test checks exactly what the field capture (the recording from the real drive) showed. Passed = the defect was found at least once on known-bad and never on fixed. Only then does the program file a test. Each known-bad run also gets a score. The score uses three yes/no checks on the analyser's finding. Did it find and pin down the same error type? Is the first rule the same as in the field? Is the verdict Confirmed? Score = checks passed / 3. Optimal (the best result) = score above 0.9 in 3 runs in a row. These three numbers are the rules of the project's diagram of how the parts fit together. That diagram says: a test score above 0.9 three times in a row is "optimal". It also says more than 10 minutes of first-level triage is a "fail".

9.6 The lab on this laptop is a pretend one; a real bench plugs in at one place

With no real drive on a bench, lab runs go to a simulated drive. It is a pretend drive made by the program (SyntheticDeviceOracle in stage2/oracle.py with GeneratorBench in testgen.py). For each error type, the pretend drive hides a secret trigger. The trigger has an ordered list of commands and a smallest queue depth. It has a range for the spacing, and a smallest block size and idle gap. It may also need a power state. And there is a 15 % chance that a run does not show the defect, even when everything is right. Real defects do not always happen either. If a procedure meets the hidden trigger, the bench writes a made-up trace with 113 columns that holds the defect. Then the real stage-1 analyser reads it. The fixed firmware never shows the defect. Instead, it writes a nearby error type as a trap. So a test cannot pass just by finding nothing. The search never sees the hidden trigger, only the rewards.

To use a real drive, write the code for run() and detect(). A starting file and a guide help you: deploy/bench_hook_template.py and deploy/BENCH_INTEGRATION.md. Then set Bench to "hook" in Settings and restart the application. The program picks the bench only when it starts. In short, write run(scenario) in app/bench_hook.py. It sends the commands with fio, nvme-cli or SPDK (tools that send commands to a drive). It saves the capture tool's recording to a file. It returns the file's path with the analyser's findings. Everything else stays the same. The program refuses commands that could destroy the drive before they reach the hook.

9.7 The regression test files

When the lab check passes, test_manifest describes the test. Then emit_closed_loop_test writes the folder suite/T-<error type>-<device>-<procedure id>/. The device is part of the name for a reason. The same error type on another drive model needs its own test. The manifest (the test's label file) lists what must be true before the test runs. One of these checks stops the test on a different drive model. How many times does the test run on known-bad firmware? Say the defect shows in a share p of runs (the measured rate). The test repeats enough times to be 95 % sure of seeing it at least once: n = ln(0.05) / ln(1 − p), between 3 and 20. Here ln is the "ln" key on a science calculator, and n is rounded up. For example, with p = 0.5 the maths gives 4.3, so n = 5.

Run a test like any Python test: cd suite/T-T-42-074e18b2 && python3 -m pytest -q. The test needs the bench fixtures (ready-made helpers) from conftest.py.

9.8 Time limit

Every lab job for a defect has a time limit. It is the first-level triage limit of 600 seconds (10 minutes, set in Settings). First-level triage is the first quick round of sorting out a defect. When the time is up, the search stops. The screen shows "first-level triage limit (10 min) exceeded" in red. The attempt then counts as failed.

10. How the database learns from your decisions (the numbers)

The project statement asks the program to learn from the admin's feedback. It must do this without training a model. Here, learning simply means counting. Each stored record has counters, like tally marks. Every decision adds to them. The counters decide what is shown first. All the rules sit in two small functions, so you can check them by hand.

10.1 Success and failure counters (a, b) and the rating

Every cause has two counters, a and b. They sit on the link "error type → cause" (table edge). Every procedure has them too. They sit on the link "cause → procedure" and on the procedure itself (tables pedge and pnode). Think of a as tally marks for "right" and b as tally marks for "wrong". Both start at 1. A third counter, n, counts how many times admins judged the record. A good decision adds 1 to a. A bad decision adds 1 to b. The rating on the screens is the share of "right" marks:

rating = a ÷ (a + b)

So a record nobody has judged has rating 1 ÷ 2 = 0.5. That means "we know nothing yet". 8 Correct and 2 Not correct give 9 ÷ 12 = 0.75. Why start at 1 and 1, not 0 and 0? So that one early "Correct" cannot make a record look perfect. Maths books call this the mean of a "Beta" spread of values. You do not need that name to use it.

The cause also keeps a second pair of counters, ta and tb. ta counts how often the lab made the defect happen with it. tb counts how often the lab did not. The Knowledge base page shows this pair as "lab reliability". "Could not be reproduced" changes only this pair. Why? A procedure that did not work on one bench does not prove that the cause is wrong.

Check it against the real database

Take error type T-42. On the link T-42 → cause c0, the knowledge base holds: a = 9.67, b = 1.0, n = 38, ta = 38, tb = 12. Rating = 9.67 ÷ 10.67 = 0.91. Lab reliability = 38 ÷ 50 = 0.76. The Knowledge base page shows exactly "admin feedback rating 0.91 from 38 decisions … lab reliability 0.76". a is not a whole number because of the slow fading in 10.2.

10.2 Four rules that keep the counters honest

Fading, 2 % per decisionEach new verdict on an error type first makes the old marks of all its causes fade a little. Only the extra counts above the start value of 1 fade: a = 1 + (a − 1) × 0.98, and the same for b. New decisions count more than old ones. So the order can change when the firmware changes.
Upper limit (cap) of 50When a + b goes over 50, both shrink by the same share until they add up to 50. So no record can pile up so many marks that new evidence cannot move it.
Shrink after an edit ×0.7When someone edits the text of a cause or a procedure, the old extra counts are multiplied by 0.7. The old text earned them, so they count for less now.
Firmware change ×0.5The event firmware_change halves all extra counts everywhere. Old evidence is worth half on new firmware.

10.3 "Record my ranking": orders, not successes

An order ("this one first, that one second") is not the same as "this one is correct". So a ranking never changes a or b. Instead, it moves a separate score, pl. The Plackett–Luce rule does this; it is a standard way to turn an order into scores. From the current scores, the program works out each item's chance of being put first. The item you put first rises by 0.3 × (1 − its chance of being first) ÷ number of items. Every item below it falls by 0.3 × its own chance ÷ number of items. The same step then repeats for second place, and so on down the list. The score enters the lookup as a gentle push (section 11.2).

10.5 "Reproduced in at least 68 % of lab runs": the safe lower estimate

Say a procedure made the defect happen in 6 of 6 runs. That does not prove it works 100 % of the time. Six runs are only a few. The Wilson lower bound gives a safe lower estimate. We can be 95 % sure the true rate is not below it. 6 of 6 → 61 %, 7 of 8 → 53 %, 8 of 8 → 68 %. Screens turn it into words: at least 80 % = very likely, 50 % = likely, 25 % = possible, otherwise unlikely. A procedure counts as making the defect happen when this estimate is at least 50 %.

11. How the knowledge base is searched for a new defect

When the program looks up a defect (section 7.1), it first turns the defect into a question to the database. The question holds the error type, family, first rule, layer, who caused it and the verdict. It also holds the device-and-firmware mark: a short code made from the firmware and the device name. Then come the analyser's tokens (short labels it writes) and a text. Last comes the order of packet kinds in the evidence rows. Each stored record is kept as a document with the same fields. The stored records are procedures, causes, earlier judged cases, error types and lessons. The search is HybridIndex.query in stage2/retrieval_v3.py.

A record gets this from every list it appears in, and the program adds them up. Then it scales the sum so that a record that is first in every list gets 1.0. So a record near the top of many lists ends up on top. That number is the "lookup match" (shown as a percentage).

11.2 Your decisions change the order

Next, the merged score is multiplied by two factors from the counters of section 10:

final = lookup match × √(0.5 + 0.5 × rating) × e0.5 × tanh(pl)

A record with rating 1 keeps its full score. A record with rating 0 keeps 71 % of it. The ranking score pl can raise the score by up to 65 %. It can also lower it by up to 39 %. The square root (√) and tanh keep both factors gentle on purpose. Here tanh is a maths function that never goes above 1 or below −1. So a record that admins often judge correct moves up. But it cannot shut out a better match. The screen shows five records. When more than five match, it shows the best 4. The 5th place is a try-something-new slot. It goes to one of the less-judged records: fewer than 5 decisions and a match of at least 0.4. Thompson sampling draws that record at random. The screen marks it "shown to give a less-tried procedure a chance". Without this slot, a procedure nobody has looked at could never earn credit.

11.3 "Seen before: YES / related / NO"

The answer comes from the best procedure in the list. YES needs four things at once. The error type is the same. The device-and-firmware mark is the same. The lookup match is at least 0.70. And the fields agree on at least 2 of 4 (rule, layer, who, verdict). related = same error type, or same family, or a very similar packet order. NO = none of these, or nothing stored.

  6. Test. The program made the folder suite/T-T-42-074e18b2/. It holds test_T_T_42_074e18b2.py, manifest.json and conftest.py. The manifest says: known-bad 6 of 6, fixed 0 of 3, optimal true, reproduced in at least 61 %. The event script_gate says admitted = true (the test was let in).
  7. More tests. "Generate test cases" built new versions of the test. It used 18 lab runs and filed two more tests. "Try nearby variations" tried 14 variations. 13 of them were likely to fail. The 3 most stressful ones were filed as tests.

What this example proves and what it does not

It proves that the whole loop works from start to end. That means finding, lookup, decision, lab, check, test and learning. It does not prove that "flush, then write" causes T-42 on a real drive. On this laptop the lab is the simulated drive of 9.6. That drive picks a hidden trigger for each error type from the error type's name. The pick looks random, but it is fixed. It does not follow the physics of the defect. The AI reviewer objected. It said the real cause is the D3hot→D0 change followed by an early access. The saved procedure does not contain that. That objection is right about the physics. On a real bench, the search would win points only from procedures that really cause the early access. An admin who knows the physics should press Needs changes and add the D3hot change. This is why every procedure needs a human decision, and a second admin, before it is approved.

14. Why it was built this way

The project statement asks for five things. First, find and pin down a defect from traces. These are PCIe traces (records of the link between computer and drive) and link-layer traces. Second, a tuner that learns by trial and reward, starting from the AI model's plan. It tunes the order and timing of commands. It wins points when the failure's pattern shows up again. Third, turn the most stressful trigger conditions into test scripts that can run in the test set. Fourth, a knowledge base that makes the fault quicker to bring back next time. Fifth, no training of the AI model. Each choice below answers one of those points, or a problem found while building it.

ChoiceWhy
Rules from the official rule books decide; the AI model only gives a second opinionA manager must be able to check every verdict. A rule names a packet and a clause (a numbered rule) in the rule book. A model answer cannot be checked the same way. It can also change from one call to the next. So the AI reviewer may disagree, and the screen says so. But it never decides.
A catalogue of 485 known error typesEngineers think in known failure types with known fixes. Each defect is matched to one entry. The entry brings how the fault happens, its usual causes, its rule-book reference and its fix (section 6.2, part 5).
One pass through the file, matching by identityReal captures are gigabytes in size. Reading row by row keeps memory use flat. The analyser follows requests by Requester ID + Tag, and commands by queue + command id. It never just takes "the next row". So the evidence stays right when traffic from many requests is mixed together.
Reuse a finished run; reuse AI verdicts by patternThe same capture or pattern must not cost time or model money twice. The cache key includes the model and the prompt version. So when the model changes, old cache entries stop matching by themselves.
Stage 2 starts only on a buttonIt calls the AI reviewer for every defect. The admin decides when that is worth it.
Saved procedure next to a fresh proposalThe knowledge base can be out of date (new device, new firmware). The fresh proposal can be wrong. The screen shows both and marks the differences. Then the admin can see which one fits the packets.
Every change is an event; tables are worked out from eventsNothing is lost. For every change you can see who made it, when, in which run, and on which device and firmware. Any decision can be undone exactly, by playing back all the other events. This is also what makes the history and the lines of extra details possible.
Counting (a, b) instead of trainingThe statement forbids training the AI model. Counters are also easy to see through. A manager can work out a rating again by hand (10.1). Old counts fade, counts have a cap, and counts are halved when the firmware changes. This keeps the counts from freezing the ranking.
Blame only what was rejected; "Could not be reproduced" is not "wrong"The admin did not touch some items. Punishing them would teach the system things the admin never said. A failed lab run often means a problem with the bench. So it is counted on its own (ta, tb).
A ranking is not a successPutting A above B says nothing about whether A is correct. Counting it as a success would push ratings up too high. So it moves only the separate pl score.
A slot for trying new thingsWithout it, a procedure never shown could never be judged. And the first one ever approved would stay first forever.
Your own version is run before it is saved as workingAn admin can be wrong too. The lab, not the person, decides whether a procedure makes the defect happen again. The person decides whether it is the right one.
Re-run the saved procedure first (regression guard)If it still works, no search is needed. This is where the knowledge base saves the most time. If it no longer works on this device or firmware, that fact is worth recording too.
A search over commands and timing with Thompson sampling, Go-Explore and confirmationThe statement asks for an RL agent (a program that learns by trial and reward). The agent tunes the order and timing of commands. Thompson sampling learns, while it runs, which kinds of change pay off. It needs no training first. The Go-Explore archive (a store of good places to start again from) keeps the search from getting stuck. Some faults do not always happen. Confirming with 8 runs and a safe lower estimate means one lucky run cannot fool the search. PPO is there as another choice.
Shorten, then push to the limitA short procedure is easier to understand and to run. The statement asks that the most stressful trigger conditions become tests. The stress climb finds them. The second test guards the edge (how far the timing can go), not just one point.
Lab check on known-bad and fixed firmware, with the same analyserSome tests fail on the bad firmware but also fail on the fixed one. Such a test is useless. The lab trace is checked with the same stage-1 analyser. So the test checks what the capture from the field showed. The fixed bench also gets a decoy (a nearby, different error put in on purpose). So "found nothing" is a real result, not just an empty trace.
Score from three yes/no checks, optimal = 3 in a row, 10-minute limitThese rules are written in the project's diagram of how the parts fit together. Three plain checks replaced an earlier weighted score. So every number on the screen is a count.
Two people for approve, retire and deleteSaved procedures become tests that other teams rely on. One person's mistake should not become the reference. The database itself refuses the change when the two names are the same.
Device and firmware on every event, device in the test nameDifferent drives need different procedures and tests. A procedure saved on one drive shows as "related", not "seen before", on another drive. It is then checked again there.
Plain words on the screensThe operators know packets and traces, not this program. Every code (T-42, P19, INC-0001) is written out in words. Every number is a count, a percentage with its meaning, or a score with its rule next to it.
A simulated drive, and one function to plug in a real oneThe whole loop must be testable on a laptop. The bench hides behind two functions (run, detect). So connecting a real drive changes nothing else.

15.2 Check a defect by hand

  1. Open the defect page. Note the "First abnormal packet" and its line in the CSV (the table file of packets).
  2. Open the CSV at that line, in the analyzer software or a text editor. Check the packet fields that the rule names (section 6.2, parts 2 and 3).
  3. Look up the rule's place in the official rule book (part 5), and check the condition. For T-42 the book is PCI Bus Power Management, and the condition is 10 ms after D3hot→D0.
  4. Compare this with the AI reviewer's opinion. If it says "disagrees", look more closely.

15.3 Check the database by hand

The knowledge base is a plain SQLite file (a whole database kept in one file). With the sqlite3 program, or any SQLite viewer, you can check every number on the screens.

You can test Undo safely. Note a decision's event number in the Earlier decisions table or in the Event log. Undo it on the Knowledge base page. Then watch the rating go back to its value before the decision.

15.4 Known limits (stated so they can be judged)

  • The lab is simulated on this laptop. See section 9.6 and the box in section 13. The loop is proven from start to end. But the procedures it finds only mean something for real hardware on a real bench (app/bench_hook.py). That hook is not written here, because it depends on your lab tools.
  • The jammer variations of "Try nearby variations" need a hardware bench that can put faults on the link on purpose. On the simulated bench they are listed as "hardware bench only".
  • Your own version that brings the error back in only 3 to 5 of 6 runs is saved as checked. But it does not go on to the lab check and a test. Its safe lower estimate is too low: 19 %, 30 % or 44 % for 3, 4 or 5 of 6. The lab check needs 50 %. Only 6 of 6 (61 %) passes. The screen still calls it "confirmed". To get a test from such a version, press Correct on it. The lab then runs it again, with a confirmation of 8 runs. Or change the rule in Stage2V3._finish if 3 of 6 should be enough.
  • A test folder is written even when the lab check fails. Its manifest.json then has closed_loop_at_generation.passed = false, and the screen says "no test filed". When you export suite/ to a test system, filter on that field (deploy/OPERATIONS.md).
  • Generated conftest.py files use the simulated bench. On a real bench, switch their fixtures to the hardware hook (deploy/BENCH_INTEGRATION.md). Fixtures are the set-up code each test uses.
  • No login. The program listens only on 127.0.0.1 (this computer). It trusts the operator name that people type. So the two-person rule is only as strong as the control over who can use the computer (deploy/DEPLOY.md).
  • The triage time saving needs your current hours by hand in the config file. Without them it shows "n/a" instead of a guess.
  • The test database on this laptop holds practice data (section 8.6). A real installation starts with an empty knowledge base.
