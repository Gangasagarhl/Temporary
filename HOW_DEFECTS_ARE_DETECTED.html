How the checker finds errors in the packets

A computer and an SSD (a storage drive) talk over a wire. Our checker program reads a recording of that wire. This page explains, step by step, how the checker finds what went wrong. It also shows which side caused it, and which official rule book says it is wrong. Every claim is backed by real lines from the 4 GB test recording.

How to read this page
  • Read the sections in order. Each one starts with a grey line that says why it is there.
  • Grey boxes in a fixed-width font are real lines copied from the test recording. They are the proof.
  • Words like PCIe, NVMe, TLP and DLLP are explained the first time they appear. All of them are also listed at the end, under "What the words mean".

1. The recording and its 113 columns

Why this part is here: everything the checker knows comes from this file. You need to know what is in it, and why the checker reads only some of it.

A computer and an SSD talk over a wire. The wire follows the PCIe rules (the rules for how packets move on the wire). The SSD also follows the NVMe rules (the rules for how storage commands are sent and answered).

A capture tool (here, a LeCroy analyzer) sits on the wire. It records every packet that goes across, in both directions. It saves the recording as a table file (a CSV file). Each line of the file is one packet. Each column holds one kind of detail about that packet, such as its time, its direction, or its type.

The file has 113 columns. Most lines fill in only a few of them, because each kind of packet has its own details. Here is one real line from the test recording:

Line 438 of the file. The computer (Downstream) writes a 4-byte value to the address FCE01008. That address is the doorbell of command list 1. (A doorbell is a number the computer writes to tell the SSD that new commands are waiting.)

Packet=436 | Link Dir=Downstream | TLP Type=MWr(32) | PSN=59 | Length=1 | RequesterID=000:00:0 | Tag=0 | Address=FCE01008 | st BE=1111 | Last BE=0000 | LCRC=0xE74C1953 | DATA=4 B | Time Delta=113.000 ns | Time Stamp=0000.399962777250s

Only the columns that have a value are shown. The other 99 columns of this line are empty.

Why the checker reads only 57 of the 113 columns

2. Sorting each line by its kind

Why this part is here: each kind of line carries different details and needs different checks. So the checker first decides what kind of line it is reading.

There are eight kinds of lines. The checker tests them in the order below and stops at the first one that matches.

OrderKind of lineHow the checker knowsWhat it is
1Packet broken on purposeJammer Phase is filled inThe capture tool changed or dropped a packet on purpose, to test how the two sides react.
2CXL trafficCXL Pkt Type is filled inTraffic for another kind of device. An NVMe SSD does not use it.

Checking "broken on purpose", CXL and side-wire first makes sure those lines are never mistaken for normal SSD traffic. The order comes from the error list (section XII.1.1, "a minimal row classifier").

3. The checker's notes about each side

Why this part is here: the old text said the checker "keeps the protocol state of both ends". This part says what that means in plain words, and why it is needed.

The capture tool sees both directions on the wire. The direction column (Link Dir) says who sent each packet. Downstream means the computer sent it. Upstream means the SSD sent it.

One packet alone rarely proves anything. An answer is only wrong if nobody asked for it. A command is only lost if the SSD took it and never said it was done. So the checker must remember what happened before.

That is why it keeps notes. For each side, it writes down what that side has sent and what it is still waiting for. Each new packet updates the notes. Then the checker compares the packet with the notes. If they do not fit the rules, a check breaks. These notes are what the old text called "protocol state" ("protocol" simply means "the rules").

  • Where the notes come from. The checker learns everything from the recording itself. It learns the SSD's address from the packet that set it. It learns where each command list is from the packets that created it. It reads the time limit for answers from the SSD's own setting (Device Control 2).
  • Why a recording should start when the computer starts. Then the checker sees the address and the lists being set up. If the recording starts in the middle, the checker says so. It does not blame anything it could not have known.
  • Why the file is read only once. The checker reads one line at a time, from start to end, and updates its notes as it goes. It never loads the whole file. So a 4 GB file needs about the same memory as a small one.
  • Where this is in the code: stage1/pcie_isolate/engine.py.

How to see who sent a line: RequesterID 000:00:0 is the computer's side of the wire, and 002:00:0 is the SSD. Link Dir says the same thing as Downstream or Upstream.

The key idea: a step can be wrong, or it can never come. Then the side that owns that step is the first suspect. For example, if step 5 never comes, the SSD took the command and never finished it. That points at the SSD.

5. The 167 checks

Why this part is here: the checks are what turn packets into broken-rule notes. A reader should know what they are and where they come from.

A check is one rule the checker tests on the packets. When a check breaks, the checker writes a broken-rule note. The note holds the check's name, the packet, the time and a one-line reason. It also holds numbers that tie it to other notes, such as the command number.

The 167 checks were written for this project. They were built from the error list and from the PCIe and NVMe rule books. No rule book contains a list called "167 rules". They come in five kinds:

Kind of checkCountTaken from a rule book?What it does
A clear break of a rule-book rule98YesThe packets do something the PCIe or NVMe rule book does not allow.
Allowed, but unusual or slow47NoThe rule book allows it, but it is rare or slow. These checks only support a problem. They never prove one alone.
Problems with the capture tool or the recording7NoLost packets, a full buffer, hidden lines, a recording that starts in the middle.
Normal actions by the computer7NoSuch as a reset or a cancel. Kept only to explain a problem, never counted as one.
Notes from the computer's own logs8NoLines from the Linux kernel log and test tools, lined up in time with the packets.

The checks also differ in how much they need to see:

  • One line is enough (46 checks). Example: a receipt that says "arrived broken" (Nak).
  • A sequence of lines is needed (36 checks). Example: a request with no answer before the time limit.
  • The bytes inside packets are needed (74 checks). Example: two open commands with the same number.
  • The whole recording is needed (3 checks). Example: a wait that is far longer than usual in this recording.
  • The computer's logs are needed (8 checks).

Why there were no false alarms: only the 98 rule-book checks can confirm that something is wrong. The 47 unusual-pattern checks can only mark a problem as "suspect". The time limits are read from the recording itself, so they are not guesses. In the normal traffic of the test recording, no packet check broke at all.

The full list of checks is in stage1/pcie_isolate/rules.py.

6. From notes to one problem, and which side caused it

Why this part is here: one error usually breaks several checks. This part shows how they are joined into one problem, and how the side at fault is chosen.

  1. Group the notes. Some notes share a number, such as the same command or the same request. Some sit close together in time. Such notes become one problem. In the test recording, 6,529 notes became 544 problems.
  2. Find the start. The earliest note in the problem is the first packet that went wrong. That is the start of the problem.
  3. Mark the follow-on breaks. Some later notes are known results of the first one. Example: a broken packet causes a "send again" receipt, which causes the packet to be sent again. Those are marked as follow-on breaks, so the reader looks at the cause, not the echo.
  4. Give the line range. Each problem says "from line X to line Y" of the file, so anyone can open the file and look.
  5. Decide the side. The checker uses the rules in the table below.

7. The 485 errors, in ten chapters

Why this part is here: it shows the kinds of errors and how many were found. It also shows which side usually causes them.

The error list has 485 entries in ten chapters. The letter in an error's name is its chapter. The number is only its place in that chapter. For example, "T-01" is entry 1 of chapter T (timeouts and time limits).

Each entry is marked as one of three kinds:

  • Seen in the packets (253 entries): the error leaves a packet that breaks a rule.
  • Partly seen (185 entries): the packets show a sign of it, but not the cause.
  • Not seen (47 entries): only the computer's logs can prove it.

What the proof looks like: three real problems

Why this part is here: it shows what you get for each problem. That is the line range, the first bad packet, the follow-on breaks, the side and the rule.

Error L-02: a broken packet is sent again. Lines 3,257,986 to 3,258,081. Side: SSD sender, or the wire.

line 3257986 START The SSD sends a write packet (Upstream MWr). Its check number (LCRC) is broken. The computer's side receives it.
line 3257992 follow-on The computer sends "arrived broken, send again" (Nak). It names packet 830 as the last good one.
line 3257995 follow-on The SSD sends packet 831 again.
line 3257996 follow-on The SSD sends packet 832 again.

The "send again" receipt went from the computer to the SSD. So the computer received the broken packet, which came from the SSD. The SSD's sender or the wire is at fault. Rule: PCIe, check numbers and receipts.

Error V-01: a doorbell value past the end of the list. Lines 6,547,325 to 6,547,345. Side: Computer. The AI reviewer agreed.

line 6547325 START The computer writes the doorbell of command list 1 with the value 1024. The list has 1024 places.
line 6547327 follow-on The SSD reports an event: "invalid doorbell value".
line 6547345 The computer's kernel log says: "nvme nvme0: Invalid Doorbell Write Value".

The places are numbered 0 to 1023, so 1024 is not a real place. The write came from the computer (Downstream), so the computer's driver made the mistake. Rule: NVMe, command-list doorbell.

Error T-01: a command is sent but never finished. Lines 12,669,916 to 12,907,641. Side: SSD.

line 12669916 START The SSD fetches write command number 226 from command list 3. No done note follows.
line 12669960 A traffic gap of 41.55 ms while work was going on. The usual longest gap in this recording is 13 µs.
+30.000 s The computer cancels command 226 (its 30-second wait ran out).
+60.000 s The computer switches the SSD off and on. The command is still not finished.

Steps 1, 2 and 3 of section 4 are there. Step 5, the done note, never comes. The first missing step belongs to the SSD. Rule: NVMe, every command the SSD takes must get a done note.

Why you can trust the result

  • No false alarms. The checker raised no problem in the normal traffic, across all 20.7 million lines.
  • Every claim points at a line. Each problem names its first line, its start, and each follow-on line. Anyone can open the file and look.
  • Time limits come from the recording. The answer time limit is read from the SSD's own setting in the recording, not guessed.
  • A second opinion. The AI reviewer reads only the lines of each problem and may point only at those lines. It checked 88 problems. It agreed with 51 and was not sure about 36. For 1 problem it agreed with the start but disagreed about one follow-on detail.
  • Limits. The checker sees only the recorded wire. It cannot see inside the SSD's program or the computer's memory. That is why 46 errors needed the logs, and 2 stayed unproven.

What the words mean

Why this part is here: so you can look up any word on this page without leaving it.

PCIe
The rules for how packets move on the wire between the computer and the SSD.
NVMe
The rules for how the computer sends storage commands to the SSD and gets answers back.
Rule book (specification)
The official document that writes down the PCIe or NVMe rules.
Rules (protocol)
What each side must send, and when. "Protocol" is the technical word for these rules.
Computer (host)
The computer the SSD is plugged into.
SSD (device)
The storage drive being tested.
Wire (link)
The connection between the computer and the SSD.
Capture tool (analyzer)
The tool on the wire that records every packet. Here, a LeCroy analyzer.
Recording (trace)
The list of every packet the capture tool saw, saved as a table file (CSV).
Packet
One small message sent across the wire. One line of the file.
Downstream / Upstream
Sent by the computer / sent by the SSD.
Request or data packet (TLP)
A packet that asks for data, carries data, answers a request, or carries a message.
Receipt packet (DLLP)
A small packet that says "arrived fine" (Ack), "arrived broken, send again" (Nak), or "I have room for more" (UpdateFC).
Wire-training signal (ordered set)
A signal the two sides send while they set up or fix the wire.
Check number (LCRC)
A number sent with each packet. The receiver uses it to see if the packet arrived broken.
Request number (Tag)
The number a request carries. Its answer must carry the same number.
Doorbell
A number the computer writes into the SSD to say that new commands are waiting, or that it has read a done note.
Command list (queue)
A list in the computer's memory where commands wait their turn. Command list = submission queue. Done list = completion queue.
Command (SQE)
One 64-byte instruction to the SSD, such as "read these blocks".
Done note (CQE)
A 16-byte note from the SSD that says a command finished, with a result number. 0 means success.
"Work done" signal (MSI-X)
A short write from the SSD that tells the computer to look at its done list now.
The checker
Our program that reads the recording and runs the 167 checks. The app screens call it "the analyser".
Check
One rule the checker tests on the packets.
Broken-rule note (finding)
What the checker writes when a check breaks at a packet.
Problem (incident)
Broken-rule notes that belong together, with a first line and a last line.
Follow-on break
A later broken rule that was caused by the first one.
Error list
The list of 485 known errors, with why each happens and how to fix it. The app screens call it "the catalogue".
AI reviewer
An AI program that reads the same lines and says agree, disagree or not sure.
The computer's logs (host evidence)
Messages the computer wrote itself, such as the Linux kernel log (dmesg).
False alarm
A problem raised where nothing was wrong.
How to read an error name such as T-42 or M-020

The letter is the chapter of the error list. The number is only the place in that chapter. It has no other meaning. On the app screens the name is always written out in full. For example: "error type T-42 (chapter T = timeouts and time limits, entry 42): D3hot→D0 transition: access before the 10 ms recovery time".
